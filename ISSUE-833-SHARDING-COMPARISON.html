Pipeline shape

NOW Single job

One runner. Two workers hit one Langflow serving all 353 tests — the contention #817 diagnosed.

e2e-daily-stable workers=2
353 @stable · fullyParallel=true
1× langflow + ollama + go-httpbin
shared backend · serializes requests
downstream (inline)
report · history · auto-remove · QA POST

SHARDED prep → matrix → merge

Each shard is its own runner + its own Langflow. Parallelism comes from the shard count.

prep
shards input → dynamic matrix (default 4)
test 1/4own langflow · w=2
test 2/4own langflow · w=2
test 3/4own langflow · w=2
test 4/4own langflow · w=2
merge 1 results.json
merge-reports → all downstream (unchanged)

Benchmark — same suite, same runner, same image

Configuration Backend Wall-clock Speedup Failures Note
baseline 1 job · w=2 1 shared ~56 min 1.0× 34 Heavy contention
chosen N=4 · w=2 4 dedicated ~28 min 2.0× 32 Best observed · 1 UI-timeout flake
N=4 · w=1 4 dedicated ~39 min 1.4× 33 Clean but serial per shard — slower

Two workers per shard won: #817's contention was two workers on one Langflow serving the whole suite. With a dedicated Langflow per shard (~90 tests each), the second worker is a net win — the residual contention (one flake) is dwarfed by the throughput.

What actually changed in code

playwright.config.ts
-fullyParallel: true,
+fullyParallel: process.env.PW_SHARD_FILE_LEVEL ? false : true, // file-level split keeps a spec file whole → @database affinity
workers: process.env.CI ? 2 : undefined, // unchanged — 2 per shard
.github/workflows/daily-stable.yml
-jobs: { e2e-daily-stable } # one job: test + all downstream inline
+jobs: { prep → test [matrix shard=1..N] → merge }
+test: --shard=i/N --reporter=blob · own services per leg · uploads blob-<shard>
+merge: download blob-* (merge-multiple) → merge-reports → 1 results.json → downstream

Guarantees & the catch

✓Preserved

  • Correctness. 31/32 failing specs match the non-sharded run — no failure hidden, none invented.
  • @database affinity. File-level sharding keeps every test() of a spec file in one shard; no cross-shard state break.
  • Downstream invariants. One merged results.json → one history entry, one QA POST, one @stable auto-removal.
  • No silent truncation. A missing shard blob raises a ::warning::, never passes green.
  • Schedule-only side effects. History/auto-remove/issue steps skip on manual dispatch.

!Why 2×, not 4×

  • File-level imbalance. Playwright balances by test count, not duration — the shard holding the slow agent/playground specs runs ~2× the fastest (26.5 min vs 12 min).
  • The slowest shard sets wall-clock. Raising N alone won't help until the heavy files are spread.
  • Tuning levers (not carved). Raise N so each shard holds fewer heavy files, or split the heaviest spec files. Decide from real timings.

What sharding does not do

Sharding is a speed change, not an error-reduction change. The ~32 failures are a real Langflow nightly regression (dev41–dev47, isolated in #816) — product bugs that run faster but do not disappear. A sharded run finding fewer failures would be a defect, not a win: it would mean coverage was lost. Reducing the failure count is a separate track — flag the regression upstream; auto-remove-stable handles the @stable churn.

Methodology. Same repo checkout, same ubuntu-latest (4 vCPU / 16 GB), same langflow-nightly:latest, N=4.

# Provider-health skips and the lane coverage verdict

> Moved verbatim from `CLAUDE.md` (#2532). `CLAUDE.md` keeps the standing rules and links here; this file keeps the mechanism, its history and its measurements. Counts and dates are as of when each passage was written. Re-measure before quoting one.

- **What a provider-health skip does to a lane's verdict (#1456)** — `collect-models` records a dead key as `inactive` and the gates skip the tests that need it, per test, correctly. What no per-test decision can change is how the **lane** reports: run [31698035402](https://github.com/oriontech-me/langflow-e2e/actions/runs/31698035402) (2026-08-13, PR #1381) said **SUCCESS** over **3 skipped / 5 passed / 1 flaky**, and the three skips were the openai targets of `agent-multi-tool-selection.spec.ts` — openai being the provider `pr-validation.yml` pins to (#1169). `scripts/lane-coverage-verdict.mjs` reads the run's own JSON report and answers in three states: `covered` (no provider-health skip), `degraded` (a skip, and something else executed) and `uncovered` (a skip and **zero** tests executed). **`degraded` keeps the lane green** — #980's trade is unchanged, and the coverage that landed on the other providers is real, just narrower and costlier — and it states what was NOT covered in the run summary rather than in a `::warning::` nobody reads (#1252). `uncovered` names a run that produced no verdict about Langflow at all — the all-skip green #570/#1012/#1010 exist to prevent, arriving by a route none of them covered. **What FAILS is a second question, and conflating the two was wrong in both directions (#1800).** Shipping `--fail-closed` on `uncovered` alone was measured too wide on the PR lane and too narrow on the daily, and the asymmetry is the lane's *unit of work*: the PR lane's "run" is whatever the import graph selected, frequently ONE spec file, so a PR editing a single wholly-gated spec during a drain of that spec's provider executes nothing and could not be merged — one dead key blocking an author who cannot fix it, #980 inverted on the lane a human is waiting on. It is reachable through **twelve** wholly-gated specs — eight on openai, two on google, two on anthropic, and **none** on a pair — a count this entry has now got wrong twice, so carry the derivation rather than the number: `provider-dependent-specs.mjs` decides `providerDependent` as `consumesModelData || tags.length > 0`, and `consumesModelData` is an AREA or a MARKER match. `provider-setup` is one of those markers, and every one of these files hits it through the very import that gives it `providerSkipGate` — so the tag is the least of it: **all 20** specs that call the gate are provider-dependent (measured; a 21st file names it only in a comment), and `consumesModelData` specs are never excluded as transitive either. The second wrong count said thirteen, *one on a pair*, and there is no pair case — the only `providerSkipGate("openai", "google")` call site is in `language-model-regression.spec.ts`, whose **fourth** test carries no gate, so that file is not wholly gated; a thirteenth file, `generalBugs-shard-3.spec.ts`, qualifies only because its other test is a permanent `test.skip`, and it is openai either way. Openai has drained **twice** here (#772, #1450), not three times — #1169's window was the *anthropic* drain, as that entry says itself. So the failing decision moved to `shouldFail()` and asks what a re-run can answer: the **account** axis — could ANY provider have served a call — read from `providers.json` rather than guessed from the report, because **a healthy provider leaves no trace in a report at all** and that is precisely why `executed === 0` was reached for as a proxy. That file says what was **recorded**, never why: `globalSetup`'s credential degradation (#1058) writes the same `inactive` records the sweep does, so every message about a dry account says "no provider was recorded usable" and points at both halves — are the keys live, and did the sweep import them — rather than asserting a drained account it cannot observe. A dry account fails; an `uncovered` run with no evidence either way fails (fail-closed on the unknown); an `uncovered` run on a demonstrably live account is reported loudly and does **not** fail — **unless the lane asks for it with `--fail-on-uncovered`**, which the daily does. That flag is the one thing #1800 did **not** get to remove, and the reasoning is the unit of work rather than the account: where the run is an import-graph selection, covering nothing means the selection was narrow; where it is the whole `@stable` suite it means something collected nothing (#1764's class), which no account state explains and which the pre-#1800 rule caught. A guard for a state a lane calls unreachable costs nothing to keep — removing it is what needed the argument. **What that leaves is not symmetric across the lanes, and reading it as a narrowing on both is the mistake to avoid:** on the PR lane it is close to a removal, because `dry` is all but unreachable there (`Collect models` is a HARD gate that already fails on "no provider probed active") and `unknown`-with-a-skip cannot occur at all (the same absent `providers.json` makes `providerSkipReasons` fail OPEN, so no provider-health skip fires) — what is left failing there is an unreadable report. That is the intended end state, the account being gated one step earlier by a check that names the cause; but it means the PR lane's coverage verdict is now a **reporting surface**, and #1456's gate on that lane lives in `Collect models`. Absent `providers.json` is UNKNOWN, never dry — the one place this guard deliberately fails open, because `uncovered` blocks a merge and a legitimately-absent optional input (a skipped sweep, a `continue-on-error` canary) must not. The daily's four shards each copy their own `providers.json` onto the tokens artifact and the merge job **unions** them: one shard reaching a provider proves the account could, and the intersection would let one shard's transient failure fail a run the other three covered. Failing whenever the **pinned** provider skipped was weighed and declined separately: the pin is an optimisation the lane applies to itself, and blocking merge over it spends #980's trade for nothing. An all-skip run with no provider-health skip is deliberately out of scope (a `@serving`-only selection executes nothing too, and #1010 owns that). The substrate is the `skip` annotation Playwright records for `test.skip(condition, reason)` — measured on 1.58.2, for the suite-level gate and the in-body one alike — which makes the reason TEXT a contract: producer (`tests/helpers/provider-setup/provider-health.ts`) and consumer read one formatter and one parser (`scripts/lib/provider-health-reason.mjs`) with the round trip unit-tested from both ends, because a consumer carrying its own copy of the pattern would fail by finding no provider-health skip at all — i.e. by reporting the run as fully covered. On the daily the reachable verdict is `degraded`, and that is exactly why the account axis had to be **a** gate: `uncovered` needs **zero** executed tests, which a full `@stable` run never produces — hundreds of non-LLM tests always execute — so the daily's gate could not fire **at all**, and the third checkbox of #1456 was answered there by the headline alone. What fires now is the reachable case: a complete report, hundreds of green tests, and no usable provider, so the whole LLM surface went unmeasured while the day read as clean. Know what that widens before reading a red daily as a regression — it is a real new way for the daily to go red, taken deliberately, and its `::error::` names the account rather than a spec. **The rotation's half is separate**: a displaced weekday slot (#1185) now renders a run-summary block naming the provider, the cause and the gap — **7 days** for a provider that owns one weekday (google, azure-ai-foundry and, since #2287, openai), **3 or 4** for anthropic, which owns two, not the "≤3 days" the rotation's own header claimed, because the weekend is not a run. The gap is derived from the schedule because it cannot be reconstructed afterwards: `param` in `reports/daily-history.jsonl` is attached per FAILING test, so a green day records no provider at all and "when did google last actually run?" has no substrate until a run-level field is added. Two surfaces carry the same decision outward: the daily's umbrella issue gets a **fifth shape** for `uncovered` and a **sixth** for a dry account (`create-failure-issue.mjs`) — the third way this step has to fire on a run whose `test` job came back GREEN, since without it the job's last step reddens the day and nothing names why (#1176). The umbrella and the run's own gate both key on the guard's `fail_recommended`, never on a second copy of the policy spelled in a YAML `if:` (#1045's shape); and the dry-account shape is **gated on the test job not having failed** (`needs.test.result != 'success'`, so a cancelled job counts too), because the account says nothing about whether specs also failed: a real failure day keeps its own title and body and carries the outage as a **banner above them** instead — dropping it there was the mirror-image information loss the first fix shipped. Where the shape does win it still **carries** any `@stable` auto-removal summary rather than replacing it (belt and braces, since the gate means the step cannot have run), while the `uncovered` shape can assert "no tag was touched" only because nothing ran. Also — and the PR lane's **declined pin** now renders the COST it paid instead of only a `::warning::`: the fallback to multi-provider is real coverage at up to 20-25x per token, on a day a key was already broken. Both shapes are chosen by POSITIVE identification, unlike the run's gate: an unknown verdict fails the run but must not label the day as a dead provider. Not wired: `scripts/run-e2e.sh` — the VM twin owns its own verdict and publish phases, and it has a Slack surface this lane does not.

# The daily `@stable` lane (`daily-stable.yml`, now on the QA VM)

> Moved verbatim from `CLAUDE.md` (#2532). `CLAUDE.md` keeps the standing rules and links here; this file keeps the mechanism, its history and its measurements. Counts and dates are as of when each passage was written. Re-measure before quoting one.

- **`daily-stable.yml`** — **Disabled since 2026-10-02 (#2159), kept as the way back (`gh workflow enable daily-stable.yml`).** The daily runs on the QA VM (`ops/vm/run-daily.sh` on `e2e-daily.timer`, see `ops/systemd/README.md`), which opens the umbrella on the destination and, since 2026-10-05, writes the history row (#2164). What follows describes the workflow as it ran; some of its guards were also wired to the VM lane (e.g. #1818). It ran on weekdays (Mon–Fri) at 05:00 BRT against `langflowai/langflow-nightly:latest`; ran only `@stable` tests; opened a GitHub issue on failure for triage (`daily-failure` label); appended one entry to `reports/daily-history.jsonl` and committed it back to `main` with `[skip ci]` (on success and failure). The `Collect models` pre-flight step shares the Langflow container with the `@stable` run and can leave it **wedged** (container alive, event loop blocked — #922/#927), so three guards keep that from costing the run: `LANGFLOW_WORKERS=1` on the service, `PLAYWRIGHT_RETRIES=0` on that step, and a health gate between the two that waits for the backend and fails with the real cause named if it does not recover (#1011). A red `Collect models` **does not** abort the shard — a drained provider key must not kill the specs that never touch it (#980). Two independent report guards run in the merge job: `shardguard` (every shard produced a blob → results are not under-counted; it runs `if: always()` so its verdict exists even when no shard produced anything to download) and `runguard` (`scripts/check-run-integrity.mjs` — the merged report actually contains tests). A **zero-test run is an infra abort, not a per-test day**: it fails loudly (fail-closed — an unknown `runguard` verdict fails too), is barred from both paths that write on the strength of the report (`@stable` auto-removal and the `spec-durations.json` refresh), and opens an issue titled *"executed ZERO tests"* instead of the usual per-test body — even when the `test` job came back green, which `--pass-with-no-tests` makes possible (#1012). **That last guarantee was a claim rather than a property until #1176, and the gap was in the one place it was most needed.** The step's `if:` carried no status function, so an implicit `success()` applied over every preceding step — and a TOTAL shard abort is *guaranteed* to fail `Merge blob reports`, because there are no blobs to merge. On run 30624101377 both of its clauses held and the umbrella was skipped anyway; everything downstream already existed and simply could not be reached. It is now `always() && …`, pinned structurally. The sibling `Auto-remove @stable from hard failures` still has no `always()` **deliberately**: it is a write path that commits tag removals without review, its own gates already bar it from an empty or partial report, and widening when it fires is its own decision. **The same abort was also invisible in the run history**, for a second reason: `append-weekly-history.mjs` `exit 0`-ed when `results.json` was absent, so `Append daily history` went green while writing nothing and 2026-07-31 is simply missing from `reports/daily-history.jsonl` — a `jq` query reads 07-30 followed by 08-03 as consecutive weekdays. It now records the day with zero totals, a synthesized reason and `report_missing: true` (additive, no version bump), which the README's existing *runs that executed NO test at all* query already selects; locally, with no run id, it still writes nothing, because that file is machine-owned and committed. **The marker says there was no merged report — never how many shards reported, and that restraint is load-bearing:** two aborts leave no `results.json` and only one of them means no test ran (every shard dying before its blob, against `merge-reports` failing on blobs the shards did write — #1726, where the zeros are *unread, not zero*). The appender cannot see blobs, so the reason is worded over the report alone and pinned by a test that refuses the word *shard* in it; the blob count that tells the two apart is `shardguard`'s, which is where `create-failure-issue.mjs` already reads it. **`reports/spec-durations.json` — the table that makes sharding duration-balanced (#936) — had never been written once until #1252, and the shape of that failure is worth carrying:** the refresh required `needs.test.result == 'success'`, which on a suite with 1–10 hard failures a day is not strict but *closed* (zero of the six dailies after #936 qualified; only 2026-07-03 in 23 entries ever had `failed: 0`, three weeks before the mechanism existed), so every daily partitioned by **file count** and one red spec out of 430 discarded 429 valid measurements. The distortion the gate guarded against is now excluded per file instead — a file counts only when every `@stable` test in it came back `expected` (Playwright's word for "passed with no retry"), `flaky` and `skipped` are both out (a skipped file measures ~0 s and would ride free onto the heaviest shard, which the green-only gate never prevented either), an absent status is undecidable rather than a pass, and **every other current file carries its committed value forward**, which is what makes dropping the gate a fix rather than a loosening. Two consequences to know: the step must never `>` into `reports/spec-durations.json`, because that path is now also its input and the redirect truncates it before `node` opens it (silently degrading to "measured this run only" — pinned by a structural test); and `mode=count` in the prep log is now accompanied by a `::warning::`, because it was always printed and nobody read it as a problem, which is how weeks of cold starts passed unnoticed. Three details of the wiring are load-bearing and pinned structurally, all three found in review of the fix itself: the step is **`if: always() && <runguard gates>`**, because a step `if:` with no status function gets an implicit `success()` and the report upload / payload build ahead of it are not `continue-on-error` — a transient artifact-upload failure would silently skip the refresh again; it is **`continue-on-error`** (#980's trade — the table is an optimisation, not a verdict, and a crash in it would otherwise redden a green daily while `Create issue on failure`, gated on the *test* job, opens nothing); and `mode` is computed over the **intersection** of the table with the files being partitioned, not over the table's size, since a table whose every key is stale (one spec-directory rename) leaves every file at the same fallback weight — a count balance labelled `duration`, with the warning suppressed on the one day it was true. One measurement is refused for the same reason `skipped` is: a file that looks clean but measures **0 s** is unmeasured, not light, and a zero in the table is a file `buildShards` can never find a lighter shard than, so all 171 would land on shard 1 (reachable in one step the day a reporter change stops emitting `duration`) — `buildShards` also treats a non-positive weight as unknown, so a hand-edited table cannot reach that state either. **The per-file rule is right one file at a time and biased in aggregate, which is what #1326 corrects:** a file is excluded when it failed, flaked or skipped, and the specs that do that here are the ones calling a real model — the slowest ones — so the table converges *on the cheap files* and the median of what is measured underweights what is not (global median 16.3 s against neighbourhood medians of 23.3–30.5 s for the eight files currently missing). The issue's own proposal — weight an unknown file at its **directory** median — was measured and **rejected**: as a point prediction it looks better (leave-one-out MAE 13.5 s vs 15.1 s), but two of the eight real cases sit in directories mixing cheap API specs with one expensive UI spec and it weights them **0.7 s and 0.5 s**, 23× and 33× lighter than today, and scored on what the daily actually waits for — the **makespan** of the partition against the true durations — it is not better at all (hiding the K heaviest, K = 4..40, N = 4: mean excess over an oracle partition **101 s** for the global median vs **113 s** for the directory median floored at it; 300 draws sampled ∝ duration: 75 s vs 77 s). LPT is robust to underweighting a minority of files. What helps, with no second mechanism, is raising the **quantile** — an unknown file is a risk and over-weighting is the safe direction, since LPT then places it first onto an empty shard rather than last onto a full one — so the fallback is the **p75** of the measured files, which beat the p50 in all 8 (shard count × regime) cells measured and in 1107 of 1912 decided paired draws at N = 4 (mean excess 79.8 s → 75.0 s; the p100 degrades to 92 s). Keep the size of it in view before re-opening: the fallback costs ~75–100 s of makespan on a ~950 s shard and nothing tried recovers more than ~25 s. The other half is reporting — `matrix` now **names** the unmeasured files and the weight they got (capped at 30, elided count printed), because "170/178 with a recorded duration" reads as a rounding error while hiding that the missing ones are the expensive ones and that a heavy spec red for a month is invisible in it (#1012). One claim of #1326's is **wrong** and is now pinned rather than restated: `@destructive` cannot be an unmeasurable entry in the partition input, because the tag is **per test** — `folder-deletion-integrity`'s destructive test is `@release @api` while its three `@stable` tests run in the normal lane and measure 22.9 s — and `playwright.config.ts` `grepInvert`s `/@destructive/` where a CLI `--grep` cannot override it, so 0 of the 459 specs the prep job lists carry it. **The listing that feeds all of this is itself environment-dependent, which cost one spec file its entire existence in this lane (#1764).** Sharding is by FILE, so the `prep` job's `--list` decides which files exist at all — and some specs generate their tests at COLLECTION time from `hasProviderEnvKeys` over `providerConfigMap`. `provider-invalid-auth-error.spec.ts` is wholly generated that way, so a key-less listing collected **zero** tests from it, kept it out of the partition, and handed it to no shard: not skipped, not red, **absent**, with `--pass-with-no-tests` keeping every shard green and the umbrella built from what ran. Three `@stable` tests asserting that an invalid API key surfaces its error went unexecuted from the lane's first day until a cross-lane comparison against the VM twin found it. Only files whose **entire** content is key-gated vanish this way — the other provider-parametrized specs keep a keyless `@stable` test, so their file survives the listing and their variants are generated at run time, which is why exactly one file was lost rather than a class of them (measured: 232 files / 629 tests key-less against 233 / 632 with the keys). The listing step now carries the three collection-gating secrets, and **not** the shard step's wider provider block: Groq, Mistral and Azure declare their tests unconditionally and skip at RUN time, so listing them would put secrets in a step that cannot use them. `scripts/daily-matrix-provider-keys.test.mjs` pins the gate, derived from `providerConfigMap` rather than re-listed, so a new `credential: "api-key"` provider becomes a requirement the moment it is declared. It asserts the **value**, not the name: `hasProviderEnvKeys` is `!!process.env[k]` and Actions renders an unknown secret as the empty string, so `${{ secrets.OPENAI_APIKEY }}` — one character wrong — declares the variable and reproduces the defect exactly, which a names-only guard passed (measured). Dummy values for the listing were rejected for the symmetric reason: they make file presence unconditional and let the matrix promise a file the shard then fills with zero tests. **#1796 closed that instance; #1812 closes the class, and the distinction is the whole reason it is a mechanism rather than vigilance.** The guard above asserts that the listing step and the shard step agree with *each other*, and they can agree perfectly while losing a file: all three secrets rotated away on the same day (both steps read `""`, `hasProviderEnvKeys` is `!!process.env[k]`, the file collects zero tests and the two sides agree about a matrix that is missing one), a future spec gating collection on a file or a capability probe, a listing that dies halfway and still exits 0. So `matrix` now also compares the listing against what is **on disk**: `scripts/declared-stable-specs.ts` walks `tests/` and reports every spec file declaring an `@stable` test, `partition-shards.mjs matrix --declared` diffs the two and **names** what left, in the same breath as the partition whose file count is the number this makes meaningful. Measured on `main` when it shipped: listed = declared, exact, and against a deliberately key-less listing it names precisely `provider-invalid-auth-error.spec.ts` — the whole point being that the report says *which* file left, not that a count moved. Four things the measurement settled and the code now encodes. Scope is `tests/**`, **not** `tests/tests-automations/`: listed files live outside `regression/` — **five** today: the four `fixtures/*-gate.spec.ts` plus `helpers/provider-setup/component-probe-gate.spec.ts` (#1934, a gate spec that lives with the helper it gates rather than with the fixtures, added 2026-09-20). It was five before #1822 took `@stable` off `collect-models.spec.ts` and is five today, with **four** in between — a different five, since that file was in the set and this one did not exist yet; re-derive the count rather than quoting it (the collector runs by path as every lane's pre-flight, so the tag only scheduled a redundant second sweep inside a shard) — so the narrower scope reports them as phantom losses, five short whatever the total is on the day. The predicate is the **AST**, never a grep for the token, for the reason recorded above — the loose substring test overcounts by 8 files — and it resolves a `test.describe`-inherited `@stable` (Playwright's `--grep` honours it, so the daily really does run such a test) and excludes a file whose every `@stable` test also carries a lane tag, since `grepInvert` removes those from every normal listing; it reuses `parseDeclaredTests`, so there is one parser rather than two that are supposed to agree. Matching is on **absolute** paths resolved through each side's own root, not on the path strings: the listing's are relative to Playwright's `config.rootDir` (today `<repo>/tests`), and a release that reported them from the config directory instead would otherwise call EVERY file simultaneously lost *and* invented — a false red big enough to get the detector switched off. And the walker uses `playwright.config.ts`'s own `testMatch` regex rather than a `.spec.ts` suffix test, pinned against the config, because a `.spec.mts` is collected there and would read as a file the listing invented. **Where it fails is the answer to #1812's open question, and the placement is the answer.** `prep` never dies on it — its product is the shard matrix, so a detector able to abort it would lose the whole listing to report one file (the same asymmetry #1813 settled for the gate-keys reporter in that step), and an absent, unreadable or malformed declaration degrades to **UNVERIFIED** rather than to agreement. The **last** step of the merge job carries it, beside `shardguard` / `runguard` / the coverage verdict, and reads `listing_verified` fail-closed (`!= 'true'`, so an unset output — the derivation never ran, a future edit broke the extraction — fails too). Running last is what makes failing cheap: the history row, the QA POST, the `@stable` auto-removal and the umbrella issue have all already recorded the day, so the run's entire product survives and only the green is withheld. It is the only one of the four axes whose evidence comes from `prep` rather than from the merged report, **by necessity** — a file that never entered the matrix leaves no trace in a report built from what ran, which is exactly why the other three cannot see it. The converse finding does **not** fail: a file listed but not declared is coverage the run *has* and the predicate did not predict (a test declared by a shared factory rather than inline would do it), so reddening the day for it inverts the trade — but it is reported loudly, because while that list is non-empty the missing list is a **lower bound**: a file the predicate cannot see is a file whose later disappearance it cannot report. **The red day also has to name itself, and the first version's own comment claimed it already did.** `Create issue on failure` is gated on the `test` job plus the two report guards, and a missing-file day has a GREEN test job — so the run reddened at its last step with one `::error::` annotation and no umbrella, which is #1176's defect on a fourth axis. That step now carries the same two clauses, read the same way, and `create-failure-issue.mjs` gains an **eighth shape** plus a banner: the shape takes the title only when nothing else did (it is last among the green-test shapes, because an abort or a dry account is a bigger story), and on every other shape the gap renders as a banner — **not** scoped away from `empty` / `partial` / `mergeFailed` the way the dry-account banner is, since a file that never entered the matrix is a fact about the run's *input* rather than about the report, and those bodies say no spec is implicated. The shape is chosen by **positive identification** (an absent `LISTING_VERIFIED` means "this lane does not track it" and labels nothing), which is the opposite reading from the gate's fail-closed one and the rule #1456 set for `uncovered`. **Three defects the review of the first version found, all of them in the safety story rather than in the detection:** `path.resolve` *throws* on a non-string, so a declaration carrying `[null]` — or a report whose `@stable` spec has no `file` at all, which the parent commit tolerated at exit 0 — left the CLI at exit 1 with empty stdout, and under the prep step's `MATRIX="$(…)"` and `bash -eo pipefail` that aborts the step and loses the day the detector exists to protect; element types are now validated on **both** sides. The check is also **one-sided** — it sees the listing shrink, never the declaration — so an empty declaration produced `missing: []` over the real key-less listing and certified it, `listing_verified=true`, with the gate passing; there is now a floor in both the producer and the comparison, the same lesson `snapshotCatalog`'s `--min-categories` records, and a *partial* declaration stays undetectable by construction, which is what the `unexpected` list is for. And the `$GITHUB_OUTPUT` emission was a `node -e` in the YAML, where swapping `${l.verified===true}` for a literal `true` **disables the whole mechanism and survives the full unit suite** (measured, both mutations) — so it moved into `matrix --github-output`, where `listingOutputLines` is asserted on its output (#1226 again, in the code written to apply #1226). One incidental find worth carrying: `process.exit(main())` **truncates a piped stdout at 8192 bytes**, because pipe writes are async and `exit` discards what has not flushed — invisible in the daily, which redirects to a file, and caught only by a test that piped the ~21 KB payload; the CLI sets `process.exitCode` instead. **The lane exclusion had to be reproduced, not approximated, and two rounds of review were needed to get there.** Playwright does not grep the tag array: `TestCase._grepTitleWithTags()` joins the FILE suite's title (the path under `testDir`), every ancestor suite's title **and** tags, then the test's own title and tags, and runs `grepInvert` over that one string. So a lane tag reaches it by four routes an exact match over `tags` cannot see — a `test.describe` title, a describe's tag array, the test's own title, and as a **substring** of a longer token (`@serving-identity`) — and each one was measured against a real `--list` as a file the listing excluded and the declaration counted, i.e. a false `missing`, i.e. a red daily and an umbrella naming a file that nothing lost. The predicate now builds that same string and tests it with `resolveLane({}).grepInvert` — `playwright.config.ts`'s own regex, imported rather than restated, so a fourth lane tag cannot need a second edit here (#1045's shape). `DeclaredTest` carries a `grepTitle` for it. Two smaller ones closed with it: the `agrees with collectStableTests` unit test compared a lane-filtered set against an unfiltered one, so the first `@stable @enterprise` test anyone wrote would have broken the unit lane rather than the detector; and a flag given an EMPTY value (`--github-output "$GITHUB_OUTPUT"` with the variable unset) threw, which is the abort the placement promises cannot happen — an empty value now degrades and only a flag with no following argument at all is a usage error. **A third round found the two routes that reproduction still missed, and they divide on whether the answer is knowable at parse time.** One is: Playwright's `tag` option is `string | string[]`, and reading only the array left `{ tag: "@destructive" }` on a describe invisible here while the runner excluded the file — `readTagsArray` now accepts the string form, which also means a `tag: "@stable"` test finally counts in Phase 0 instead of warning, the same *runs in the daily, invisible to the generator* gap the describe-level warning beside it exists to prevent (zero occurrences today, so no generated count moved); and a describe `tag` that is genuinely unreadable (`tag: LANE`) now travels down to its children, whose lane status is then **undecidable** and votes for neither `files` nor `laneOnly`. The other is **not** knowable: a TITLE built from a template substitution is greppable at run time and opaque to an AST, and **19 of the declared files carry one** — almost all of them the provider-parametrized specs, #1764's own family. Note the construct: it is the whole grep string, so the test's own title counts as well as its suites', and the two populations differ (20 files have an interpolated *describe* title; one file in the bucket has no `test.describe` at all) — which is why every surface is worded over *a title* rather than over a construct the file may not contain. Dropping them would blind the check exactly where it exists to look, so they stay counted and the doubt is carried instead: `unresolvedTitles` on the declaration, `unresolvedMissing` on the verdict (the intersection with what is actually missing), a line under the MISSING list saying a lane tag reaching such a title at run time would look identical to a lost file, and the same caveat in the umbrella's triage pointer. Both are worded over the CAUSE — *a title built from a variable* — and not over one of its shapes, which took two passes to get right: naming `test.describe` misdirects the test-title case, and naming *the interpolation* misdirects the identifier case, since a describe title the parser cannot read at all reaches the same bucket by a different branch. **A fourth round caught the widening going one shape too far, and the failure was the one this whole entry is about — a guard going quiet.** `literalText` renders a template with substitutions as its SOURCE, which is right for a title (Phase 0 publishes `${provider}` on purpose) and wrong for a tag: `` tag: `@${T}` `` came back as a successfully-read tag whose text the parser knows is not the runtime value, and **three fail-closed guards stopped firing at once** — `check-checklist-coverage`, `stable-tests --check` and `assertNoWarnings` all went from refusing it to silence. Tags now read through a stricter `literalTagText` (string literal or no-substitution template only), which also closes the same hole in the ARRAY form, where it pre-dated all of this. Two wordings went with it: the `unparseableTags` message, now that the flag is INHERITED from a describe, cited the child's line while the unreadable option sat three lines above it; and `unresolvedTitles` was described as a describe title. So the standing limit is: the predicate reproduces Playwright exactly for literal titles and literal tag options, and reports where it cannot — with one known benign gap, `test.only`, which Playwright lists and this parser skips (it surfaces as listed-only, never as missing, and `forbidOnly` makes it unreachable in CI). **Wired to the VM twin too (#1818), and there it is the point rather than parity.** `scripts/run-e2e.sh` derives the declaration beside its own `--list` and fails the run in `phase_verdict` — its last phase, after the report, the metadata and the history row are written, the same placement and the same fail-closed reading as the Actions gate. **It fails unconditionally there, and the conditional version is the instructive part.** The first fix tied severity to the collection-gate plan, because `REQUIRE_PROVIDER_KEYS=0` invites the operator to *accept the narrower comparison* and a spec generated entirely from an absent key is what that costs. Measured, that killed the mechanism on the only lane it was added for: the flag **defaults** to 0 and this VM has no `GOOGLE_API_KEY` on purpose, so `narrow` is not an opt-in there but the lane's permanent state — every cause would have been downgraded, including the ones #1812 exists to catch. The same measurement removes the motive: with only google absent the clone loses **nothing**, and it takes all three keys blank to lose one. What the narrowing buys is a comparison whose *counts* are not comparable; it was never a licence to report a lane green over specs it did not run, which is #1010/#1012 one level down. So the contradiction was resolved in the **prose** — `phase_prep`'s narrow warning now states that consequence instead of promising a passing run. `phase_prep` does **not** die on a broken derivation, and the asymmetry with the collection-gate check three blocks above it (which *does* stop the run) is argued in the script: the gate is an INPUT to every count the run produces, while this is an AUDIT of the listing, and an audit that aborts the run it audits is the shape #1812 spent a review round removing. The durable half is a `listing_completeness` block on the history row — `{verified, missing}`, additive to schema v1 — written by **both** lanes, because with one writer `scripts/compare-lane-verdicts.mjs` sits permanently on *parity UNVERIFIED*, which reads like a check and is not one (the reachability trap `langflow_version` already documents). Three states, and the middle one is why it is not a boolean: `verified: true, missing: []` is checked and complete, a non-empty `missing` names the files that entered no shard, and `verified: false` is **unknown**, which is not the same as nothing missing (#1012); the block's absence means the lane does not measure it. What it buys the comparison is one sentence: on a test-count difference the comparator used to guess *"they may not have run the same suite revision"*, and now it **names the file** — which is the difference this lane exists to classify, and the one it mis-attributed twice as a catalog problem. Covered by `npm run test:units` (the predicate and the producer end to end) plus `npm run test:scripts` (the diff, the renderer, the output emission, the umbrella's eighth shape, and the daily's gate **executed** under `bash` rather than spelled — #1226's lesson). A **third** report guard runs beside those two (#1456): `runguard` counts `skipped` inside `tests_total`, so a day whose only `@stable` results were provider-health skips reads as a complete run of N tests. The coverage verdict answers whether those results were verdicts at all — report-only, with the gate in the job's LAST step and read fail-closed there — see the coverage-verdict bullet below.
- **Scheduled lanes beside the shards (#2142).** The VM daily (`ops/vm/run-daily.sh` exports `E2E_LANES="destructive serving"`; `scripts/run-e2e.sh` keeps it empty for every other caller) runs the tests that carry `@stable` **and** a lane tag, under that lane's flag. What each lane runs is decided by `scripts/lane-selection.mjs` over `scripts/lib/scheduled-lanes.mjs`, so the shell only orchestrates (#1226).
  - **`@destructive`** runs on shard 1's backend once that shard's `@stable` round is over, with `PW_DESTRUCTIVE=1` (the config pins `workers: 1`), before the backend stops. The policy specs are instance-global and the others wipe account-wide state, so nothing else may share the instance; this is the order `pr-validation.yml` already uses.
  - **`@serving`** runs after the shards on `SERVING_PORT` (default `BASE_PORT+8`, 7878 on the daily), one variant at a time: `trusted`, `untrusted`, `required`, the three states `scripts/start-langflow-serving-identity.sh` starts. They are applied as instance environment to the run's **own** served artifact (the venv), not to a Docker image, so the lane tests the same build as the shards. Each spec is mapped to the variant it asserts. A listed spec mapped to none fails the run, and a unit test fails first for any `@serving` spec in the tree that maps to no variant or to two. Source targets only: `E2E_LANES=serving` with `TARGET_KIND=image` is refused at start.
  - **Reported like the shards.** Each lane round's blob lands in `all-blobs` as `lane-<lane>-<run>-*.zip` and merges into the day's report, so `runguard`, the umbrella, the history row and `@stable` auto-removal all see it. The shards' blob guard counts `shard-*.zip` only, so a lane's blob can never stand in for a dead shard. A second guard requires a blob from every lane run that had a test selected (`lanes_complete`, `lanes_missing` in `run-metadata.json`).
  - **Listing completeness, per lane.** Each lane lists its own selection (`--list` under its flag) and compares it with `declared-stable-specs.ts --lane-env=<flag>`. The verdict fails on a lane it cannot verify, on a file missing from its listing, or on a lane run that left no blob.
  - **Empty is normal.** A lane with nothing promoted to `@stable` declares nothing, lists nothing, is verified, and starts no backend. That is its state until its tests are promoted one by one through the usual validation; the orphan reconciler keeps treating lane-tagged tests without `@stable` as out of the daily by design.

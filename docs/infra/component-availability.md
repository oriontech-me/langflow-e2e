# Component availability, catalog drift and spec-doc path guards

> Moved verbatim from `CLAUDE.md` (#2532). `CLAUDE.md` keeps the standing rules and links here; this file keeps the mechanism, its history and its measurements. Counts and dates are as of when each passage was written. Re-measure before quoting one.

- **Component availability is a packaging decision, per image (#1040)** — `docs/component-distribution-policy.md` is the standing answer, so it stops being re-decided per incident (it was decided wrongly twice: #898 and #907 were both attributed to missing `langchain-*` extras when the 1.12 packaging split was at least as much the cause; #1039 corrected the record and demoted the Groq/Mistral specs). Most families moved out of `lfx.components.*` into per-vendor distributions plus an aggregate `lfx-bundles` the nightly does **not** install; the old paths are shims deleted at **M4**, which has **no published date and no target release** — searched exhaustively for #1297 and recorded with its negatives in `docs/component-distribution-policy.md` so nobody repeats it. **No DATE appears anywhere** — not in any issue, PR body or comment thread, not in the 703 Discussions, not in the release notes, and not in milestones the repo does not use; and the TOKEN `M4` has never appeared in any markdown revision upstream has ever had (`git log --all -S "M4" -- '*.md' '*.mdx'` is empty — `*.mdx` in the pathspec deliberately, since git's `*.md` does not match it and the docs site is all `.mdx`; the control `-S "M1"` over the same pathspec is non-empty, which is what proves the pickaxe finds M-tokens in markdown rather than proving nothing). That kills the plausible "an earlier `BUNDLE_API.md` listed it" theory. **The reason it is unresolvable is that M1–M4 are defined in a document that is not in the repository** — the internal *"Bundle Separation: Developer Guide"*, cited by section number from `scripts/migrate/check_router_trust.py` and `src/lfx/src/lfx/extension/init_template.py`, tied to Jira `LE-1017`. What IS public is M4's **shape**: **five** PR bodies carry the token — four about bundles plus #11983, whose *"address M4"/"M5"* commit lines are a different internal M-sequence, recorded so a re-run that finds five does not read as a different query — two of which say what it is (#13568, #13577 — *shim removal, one loud deprecation minor first*, merged into their stack branches 2026-06-11 and reaching a release line 2026-06-23 via #13563). That yields a floor rather than a date, and the floor is the useful half — measured on `origin/release-1.13.0` (tip `a43ed6fbca`, the newest line in development), **78 shim directories under `components/` and not one `DeprecationWarning`** (nor any central warn path), so the loud minor has not shipped and is not 1.13 either: **M4 should not land before 1.14** — *should*, because the floor has **two** soft joints and naming one is how it gets quoted as a bound: "one loud minor first" was stated intent in June 2026 and not a commitment, and nothing forces either the warning **or the removal** into a minor rather than a patch (a warning in 1.13.x and a deletion in 1.13.y satisfies the stated shape and beats 1.14). The version-independent form is the one to rely on: **not before the release after whichever release first warns**, and nothing has warned. **The most recent statement is #14790 (open, 2026-08-27, external contributor) and the tree contradicts it, which is the finding** — it reads as though new bundles now ship with **no shim at all** (true of #14549), but `release-1.13.0` carries **78** shims against 1.12's 77, the 78th being `plivo` from #14396 (merged 2026-09-03, after #14549) with a full shim **and an amendment to upstream's own freeze baseline** (`scripts/ci/frozen_component_dirs.txt`, untouched since #13563). So the surface is **not** frozen and not only shrinking — two cases for it against one that plainly shipped a shim — and `check_components_frozen.py` is not the enforcement either: by its own docstring it is an additions-only gate against a committed baseline, which #14396 simply updated. Shims *are* also deleted piecemeal outside M4 (`f28337bf8f`), so the set moves in both directions; count it per ref instead of assuming. Two traps sit in front of anyone re-checking this, and the first one bit this very entry. **REST cannot answer "does any discussion mention M4", but not because the endpoint fails** — `gh api …/discussions` returns `HTTP 200` and a page of 30; what REST has no notion of is text search, so the question needs GraphQL `search(type: DISCUSSION)` (an earlier version of this sentence claimed the endpoint returned nothing, which is false, and a documented trap that is itself wrong is worse than none). And the release notes' *"bundle separation concludes in 1.12"* is about which provider bundles the default install ships, not about deleting the shims — the same sentence promises *"existing component class names remain compatible"*, so reading it as the M4 date inverts its meaning. Measured on the image `1.12.0.dev10` for what is installed (21 `lfx-*` distributions, no `lfx-bundles`) and **36** categories / **189** component types in `GET /api/v1/all`; and on `origin/release-1.12.0` — the line the nightly is cut from, **not `main`** — for the tree: **106** `lfx/components/*` directories, **79** shims (77 `lfx-bundles-shim` + 2 `lfx-compat-shim`), **27** core. The ref is part of the measurement — the first version of this entry recorded main's split against a nightly — but **which** ref differs has changed: `main` used to read 78/28 because `cassandra` became a shim on the release line only, and that **merged back** on 2026-08-18 (`c3bfdb7d03`, #14652). Re-measured 2026-09-05, `main` and `release-1.12.0` both read 77 bundles-shim / 2 compat / 106 dirs / 27 core, and the line that now differs is `release-1.13.0` at 78 / 2 / 107 / 27. The load-bearing rule holds in **one** direction: **no category appears for a family the image does not ship** (every shim with a category has its distribution installed, 10 of 10; the other 69 have none). The biconditional is false — 11 of the 27 core directories produce no category at all, and three installed distributions have none of their own (`lfx_datastax` supplies two, `lfx_vllm` and `lfx_openai_compatible` ship no components) — so a directory count never predicts a catalog. Two shim flavours, and the difference changes the diagnosis: a `lfx-bundles-shim` family really moved and raises `ModuleNotFoundError` naming its distribution, while a `lfx-compat-shim` is an internal rename alias (`knowledge_bases` → `files_and_knowledge`) with no distribution and no error at all — checking whether a package is installed answers nothing for it. **The source tree and the catalog do not correspond 1:1, and reading the tree to answer an availability question will mislead you**: `knowledge_bases` is a *shim* directory while the `Knowledge` component is present under the **`files_and_knowledge`** category. Installed also ≠ buildable — with `lfx-bundles` present but `langchain-groq` missing the component is placeable and fails at run time, which is why `probe-component-available.ts` (presence) and `probe-component-buildable.ts` (#900, builds) both exist. **`globalSetup` reports catalog drift** against the committed baseline `tests/assets/catalog/component-catalog-baseline.json` on every run (one request, 70–85 ms / 524 KB), so a vanished family is named at the gate instead of surfacing as a `waitForSelector` timeout 30 s into a spec (#884's misclassification tax). It snapshots `category -> component types` rather than the category list #1040 asked for, because a **reparented** component breaks a spec just as thoroughly while category-level drift shows nothing — such a component is reported `MOVED`, not as an unrelated removal plus addition. It **warns, never fails** (#980: a new category costs nobody a test, and a removed one is legitimate when the image dropped a distribution we do not test), but never reads as clean without a verdict — an unreadable baseline, a **malformed** one, a failed request and a **200 carrying no categories** each report `UNKNOWN` with the reason named (#1012). **"Warns, never fails" was not a property of the first version, it was a claim, and the difference cost a whole run:** the comparison sat outside both try blocks and the baseline was validated only far enough to know `categories` was an object, so the most natural hand-repair — pasting the raw `GET /api/v1/all` body, whose values are `{type: template}` objects and not arrays of type names — parsed, passed, and threw `TypeError: types is not iterable` out of `globalSetup`, aborting with **zero tests executed** (`runguard`'s infra abort). The comparison is now `catalogVerdict`, a pure function that **cannot throw**, with `globalSetup` holding nothing but I/O — which is what makes the guarantee unit-testable instead of asserted, and the layering shows under mutation: dropping the shape guard costs *attribution*, dropping the outer catch costs the run. The **200-with-no-categories** floor is the same class of false verdict from the other side: `snapshotCatalog` is tolerant by design, so `{}`, `null` and `{"detail": "Not authenticated"}` all normalise to zero categories and used to diff as *every* category gone — 36 lines each claiming specs would time out, on a still-building registry. The writer already refused that state (`--min-categories`, default 20); the reader had no floor at all, and the floor is 0 here vs 20 there on purpose (a wrong baseline is permanent and silent; a real-but-small catalog is drift a human should still see). Accept expected drift with `npm run catalog:baseline`, which is a **committed** diff on purpose: a self-updating baseline would make every catalog change invisible exactly once. Traps encoded in `component-catalog-drift.ts`: `component_display_names` is a **metadata map, not a category** (189 entries keyed by the lowercased type name — folding it in would add a 37th pseudo-category listing every component twice; the *stronger* claim that it makes reparenting undetectable is false, since the keys are lowercased and only `policies`, 1 of the 189, is already all-lowercase); a removed category whose components all **survived elsewhere** must not claim "specs will time out", so the report counts and now **names** what actually vanished (a count alone left the reader hand-diffing the baseline in a mechanism whose whole claim is that the cause is named); and the category keys are **sorted**, because `componentIndex` is last-wins over a relation that is not 1:1 — with insertion order, one type registered by two distributions reported a phantom `MOVED` on an *identical* catalog, a warning no baseline refresh could ever silence. Also measured, and re-measured 2026-09-05: the repo's hardcoded `lfx/components/...` references went from **29 across 21 files** to **61 across 46 files** — and **zero** still point at a shim, so M4 breaks none of them today (#1040 assumed otherwise). The growth is #1298/#1314's doc-path sweep writing *correct* paths where docs carried dead ones, not new coupling; the three families new to the table (`utilities`, `prototypes`, `agentics`) are all real directories. The figure counts **our own prose**, so it moves whenever a doc names a component path — re-run the grep rather than quoting the number. The grep did find `components/agents/agent.py`, which **no longer resolves on any current ref** (it existed from #9133, 2025-09-02, until #10180, 2025-11-12 — stale, not fictional, and the first version of this entry said "never existed"), plus **20 more dead paths of the same class** outside that spelling: 18 occurrences in 16 spec docs of the pre-`lfx` `src/backend/base/langflow/components/…` tree, and 2 writing `src/lfx/components/…` without the real `src/lfx/src/lfx/` prefix. All 21 **were** the #1092 failure mode — a nonexistent path is silent — and **#1298 closed it, sweep and guard in the same PR (#1314)**: the 21 are corrected, and resolving *every* doc against four real refs found **42** unresolvable paths across 35 files rather than 21, because ~20 more were reorganised `src/frontend/` paths outside the `lfx…/components` spelling that grep looked for, plus 10 written as an ellipsis — a defect and not a skip, since no ref can confirm one (#1012). **Two scripts with adjacent names, and only one of them resolves anything; reading the wrong one has already cost a review** — on PR #1570 the guard had failed the PR, and the review reported it as nonexistent. `scripts/validate-spec-deps.ts` checks only that the mandatory `## External dependencies` section is **populated**, always exits 0, and is reachable solely through `npm run validate:specs` — nothing under `.github/` runs it. `scripts/watch-upstream-areas.mjs --mode=check-docs` **resolves** every backticked `src/…` token in that section, and runs on every PR as `pr-validation.yml`'s **`Spec-doc dependency paths`** job. It is a **sibling mode**, not `--mode=check` extended as this entry once predicted: `check` scans the `lfx` subtrees and needs a real working tree, while `check-docs` reads through `git ls-tree` — which is what lets the lane resolve against a blobless `--depth 1 --no-checkout` clone (520 KB / 1.6 s measured, against ~117 MB to materialise the files). Severity follows the diff (#980): a path in a doc **the PR changed** fails, a pre-existing one is a `::warning::`, so one upstream rename cannot redden every PR that edits an unrelated doc — and cannot be invisible either. Since #1574 it resolves against `origin/main` **plus the two release lines the nightly is cut from** (derived, never hardcoded — `release-1.9.7` sorts above `release-1.12.0` lexically), and a path resolving on only some of them is named in a `::notice::`, so a green verdict never silently reads as "exists on `main`". Re-measured 2026-09-05: **589 paths, zero unresolved, zero `::notice::`** (against `origin/main` plus the derived pair, which on 2026-09-05 is `release-1.13.0` + **`release-1.12.1`** — cut 2026-09-01, the day `v1.12.0` shipped, so the rotation `RELEASE_LINES_TRACKED`'s own comment predicted would "vanish silently" had already happened when this was measured; name the rule and print `--mode=release-ref` rather than quoting a ref) — spread over the **178** docs that declare any, out of 294 scanned (1 exempt), since the guard's own `from 294 doc(s)` line counts what it read, not what declared. The one path that used to resolve on `release-1.12.0` only now resolves everywhere, which is the same back-merge recorded above. **A third mode answers the question `check-docs` structurally cannot (#1592), and the distinction is the whole point:** `parseDocDeps` hands the resolver only the tokens that start with `src/`, so a doc writing `api/v2/hitl.py` has no path that fails to resolve — it has a path the resolver never sees, and the count that line prints counts what it was GIVEN, never what the docs depend on. That is #1092's silence moved one step earlier, and no guard in the repo could see it: measured 2026-09-18, **52 upstream modules across 28 docs** were named that way, plus **2 abbreviations that matched two real files each** (`session-selector.tsx` is a live file in both `src/frontend/src/components/core/playgroundComponent/chat-view/chat-header/components/` and `src/frontend/src/modals/IOModal/components/IOFieldView/components/` — the guard cannot tell them apart and neither can a reader; write them in full, in a paragraph about writing paths in full). `--mode=check-doc-abbrevs` reports a non-`src/` token that resolves by SUFFIX to exactly one upstream path and to nothing in **this** repo; correcting all 52 took the `check-docs` count from **730 to 782** on the same base, which is the only visible evidence coverage widened. Uniqueness is what makes it gateable rather than noisy — measured over the whole of `docs/`, the prose that survives every other clause (`text/event-stream`, `store/tags`, `models/gemini-embedding-001`) resolves to **nothing**; pick the example from the right clause, since `@modelcontextprotocol/server-everything` is rejected by the `@` in the character filter and never reaches the tree, so citing it for uniqueness disproves the point it is quoted for. *Ours-wins* is load-bearing rather than tidy: upstream carries `src/frontend/tests/utils/flow/add-component-from-sidebar.ts` and so do we, so a suffix match alone rewrites **17 references, 10 distinct tokens across 10 docs**, into Langflow paths. **A wrong abbreviation is half-visible, and the half that is not was measured (#1925):** an abbreviation that is also WRONG resolves to nothing by suffix (`playground-message-logs.md` wrote `tableComponent/TableOptions/index.tsx` for a path carrying one more `components/` segment, corrected by hand in #1592), and falling back to the basename was REJECTED — ~130 rows that are almost entirely HTTP endpoints, `POST /api/v1/flows/` matching the seven upstream directories named `flows`, with the one true positive resolving **456** ways. What cleared #1925's bar (false positives in the single digits) is the **gapped** rule: a FILE token whose written segments occur, in order, in exactly **one** upstream file is reported as a segment left out, same severity and declarations as a plain abbreviation — **zero** false positives on today's `docs/` and on the pre-#1592 corpus (`ad2271fc3^`), where the TableOptions token is its only hit; today that file is written in full, so the rule reaches nothing today. Directory tokens are excluded because the same relation's one hit there is `ollama/ollama`, a docker image. A segment written WRONG rather than omitted (`components/agents/agent.py`) stays invisible: a substitution rule's only hit today is that token, which matches two files and sits beside its full path as history. A token named to say the spec does **not** depend on it is declared in `scripts/lib/doc-dep-abbreviation-declarations.json` (4 entries, verified in both directions per #1084: a declaration that silences nothing is reported as expired), never as an in-doc sentence giving a reason to omit — that form is exactly #1587. One test earns a caveat rather than its name: the unit lane's whole-repo assertion builds a **synthetic** tree from the `src/…` paths the docs already declare, so it needs no checkout and reaches only abbreviations some *other* doc spells out — **22 of the 52** corrected occurrences (18 of the 48 distinct modules), measured by reverting one at a time, with the complete check living in the PR lane. It is named for what it checks after reverting `hitl.py` left it green (#1226's shape, caught before it shipped). **Two things review caught in the first version of this entry are the durable lesson:** the CLI half was pinned by nothing — `process.exit(1)`, the `::error::`/`::warning::` choice and the whole expired-declaration report could each be deleted with the unit lane green, the same gap the sibling `check-docs` harness was built for — and one DISJUNCT of the stale-declaration escalation was dead in the only lane that runs it — `changed-docs.txt` is built with a `-- docs README.md` pathspec and an `.md$` filter, so the declarations file could never reach the list the severity rule reads, while the other disjunct (the diff touched the doc the declaration names) was always live and covers the commonest expiry. Both are fixed and mutation-checked; the second is pinned by EXECUTING that workflow step's `run:` body under `bash`, not by grepping the YAML, which is #1226 one more time. **A third round then caught the correction itself being the same error twice:** "24 of the 55" was replaced by "18 of the 39", which pairs the distinct-MODULE numerator with a denominator invented by a diff locator that silently dropped every line where two tokens changed — the mixed-unit sin the replacement indicted its predecessor for. Ground truth is a line-for-line multiset diff against `origin/main`, which needs no alignment heuristic. The same round found `delete-flow.ts` cited as an ours-wins example in a code comment when it exists **nowhere** upstream — the identical wrong example this work had already corrected in the JSDoc thirty lines above, so one of two copies was fixed and the other read as measured fact.

# `pr-validation.yml`

> Moved verbatim from `CLAUDE.md` (#2532). `CLAUDE.md` keeps the standing rules and links here; this file keeps the mechanism, its history and its measurements. Counts and dates are as of when each passage was written. Re-measure before quoting one.

- **`pr-validation.yml`** — Runs on every PR to `main`. Parallel jobs: TypeScript check (`tsc --noEmit`, plus **three** unit lanes — `npm run test:scripts` for the dependency-free `.mjs` helpers under `scripts/`, `npm run test:units` for everything in TypeScript, and `npm run test:pipeline` for the deterministic issue pipeline under `.claude/skills/`), ESLint, the **QA-CHECKLIST guard** (generated blocks untouched + spec↔doc↔checklist triad, see below, plus the `@stable` ownership guard — see its bullet), and the impacted-specs E2E run. **The third lane exists because the first two could not reach it, and nothing else did either** (#1593): the pipeline that owns phase order, every gate and the evidence a PR's Validation block is written from — 2.8k lines, 119 passing tests — was run by **neither** unit lane and typechecked by nothing. `test:units` globs `.`, `scripts/` and `tests/`, never `.claude/skills`; `test:scripts` globs `.claude/skills` but only for `*.test.mjs`; and the root `tsconfig.json`'s `include` stops at `scripts/**`, so `npm run typecheck` never opened the directory (a `PwStats` fixture there had been missing a required field since `backendErrorLines` was added). It cannot simply join `test:units`: the pipeline imports with explicit `.ts` extensions under `moduleResolution: bundler`, which `ts-node/register` **cannot load** — measured, 0 pass / 1 fail — so the lane runs `tsx` (now a pinned devDependency rather than an unpinned `npx` download) plus `tsc -p` against the pipeline's own tsconfig in the same step. All must pass before merge. The E2E job shares one Langflow service container between its `Collect models` pre-flight and the specs, so it carries the same two guards as `daily-stable.yml` (#1019): `PLAYWRIGHT_RETRIES=0` on the pre-flight, and a health gate between the two steps that waits out the post-sweep wedge (#922/#927) and, when it does not clear, fails naming the real cause instead of letting `globalSetup` report an unattributed 120 s timeout. Both are gated on `needs_models`, so an LLM-free PR pays for neither. **The E2E work is selected by import graph, not by changed-spec glob** (`scripts/impacted-specs-by-import.mjs`, #1054): a changed helper or Page Object selects the specs that import it **transitively**, because selecting only changed `*.spec.ts` let the highest-reach change the repo can receive run zero specs (PR #1052 changed a helper reached by 112 specs; PR #1088 one imported by 135 — both reported `skipping`). A changed spec still selects itself, so the old behaviour is a subset. `tests/fixtures/**`, `playwright.config.ts` and the global hooks are **suite-wide**: they resolve to every spec and raise a visible warning. **What that warning asks for changed in #1174, because what it asked for could not be done** — it told the reviewer to dispatch `manual.yml` *for the full suite*, which that lane has never been able to finish; it now names `test_tag=@stable` and says what that leaves out, per the bound in the `manual.yml` bullet below. The selection is capped (`IMPACTED_SPEC_CAP`, default 20, `@stable` first within each tier) and **never silently** — the dropped specs are listed in the job log and the run summary (#1012's rule). **A CI-only diff no longer skips** (`scripts/ci-change-coverage.mjs`, #1159): nothing under `tests/` imports a workflow, so the import graph honestly returns zero and the lane used to prove only that the change *parses* — PR #1157 rewired four workflows onto a new composite action with every check green and the E2E lane `skipping`. The classifier answers the other half — *does the PR lane run what changed?* — deriving reachability from the YAML itself (a workflow's `scripts/x` refs plus its `uses: ./.github/actions/y`, and each action's own refs, which is how `wait-for-backend.mjs` is reached without being named in `pr-validation.yml`). Verdicts: **`canary`** (the lane's own workflow, an action it uses, or a script it reaches changed) runs a fixed 3-spec set — two `api/flows` specs plus one UI spec, all `@stable` and LLM-free — so the lane boots Langflow and walks pre-flight → health gate → Playwright for real; **`dispatch`** (the surface belongs to another lane) names the workflows to dispatch instead of implying coverage; **`vm-only`** (#2173) covers a surface only the QA VM lane runs (`ops/**` and the scripts its shell reaches: `ops/vm/run-daily.sh` → `scripts/run-e2e.sh` → the `@stable` removal scripts, which commit to `main` without review). The classifier names the unit tests that cover the file, found by sibling `*.test.*` or by import, and says its first real run is the next VM daily. Before #2173 those **48** files read as `none` ("no CI surface at all"). **`none`** stays silent. Since #2192 the scan reads what a lane RUNS rather than what it spells: comments are dropped (a `pr-validation.yml` comment naming `run-e2e.sh` had flipped it to `canary`), `npm run <name>` is followed through `package.json`, a skill's own `scripts/` is a second script root, and a diff that also impacts specs is classified too (`--specs-selected`: its specs run, never the canary, and only the advice is printed). **Naming a workflow was not the same as naming a remedy, and from the day it shipped (2026-07-30, #1159) it did the first while claiming the second** (#1609): the verdict never checked whether the workflow it prescribed *can* be dispatched. Measured on PR #1608, a change to `scripts/coverage-summary.ts` produced `Dispatch .github/workflows/update-coverage-summary.yml on this branch before merging` for a workflow that is `on: push: branches: [main]` — `gh workflow run` answers `HTTP 422: Workflow does not have 'workflow_dispatch' trigger`, on any branch, forever. An instruction nobody can carry out is indistinguishable from silence, which is the one thing this verdict exists to remove (#1092 in a new costume). So the triggers are read and the advice is **rendered by the classifier**, in six cases: dispatchable; **not on the default branch yet** (404); **disabled in Actions** (422); no trigger; triggers unreadable; and triggers *this PR edits*. A single diff mixes them — `scripts/stable-tests.ts` names daily-stable (disabled) and update-coverage-summary (no trigger) at once — so the message is **split, never flipped on its worst member**, which on the motivating case would withhold the one dispatch that does work. **Three things make this more than a trigger check.** The trigger that counts is the one on the **default branch**, not the branch you dispatch (the rule `issue-contract-guard.yml` already records in its own `on:` block), so the lane hands over the **default branch's** `.github` tree via `git archive` — the default branch, not the PR base, because that is the semantically right input and **not** because a live hole was closed: this lane is `on: pull_request: branches: [main]`, a filter on the base, so it can never see a PR whose base is not the default, and the two are the same value by construction here; reading the head copy would have told a PR that *adds* `workflow_dispatch` — #1609's own Option B — to dispatch a workflow that does not have it yet, i.e. reproduced #1609 one PR later. A workflow **disabled in the Actions tab** 422s however good its YAML is, and ours have been (`daily-stable` since 2026-10-02; four more until #2171 deleted them), so the lane also passes the API's state listing (`actions: read`); both inputs are fetched only when the diff touches `.github/` or `scripts/`, and both carry a **non-empty floor** — absence from the listing means *not on the default branch*, so an empty one is not a weak signal but a 404 claim about every workflow at once (`gh` can exit 0 having written nothing). And the two sources **disagree only when a workflow the PR adds has already registered itself with Actions**, so absence from *either* wins over presence in the other. The trigger half fails **closed** (unreadable ⇒ unknown, never "probably yes"); the Actions-state half fails **open** (no listing ⇒ the trigger alone), because caveating every instruction over a lookup that usually succeeds is the noise that gets warnings ignored (#1252). A doubt — `unreadable`, or `this PR edits that file` — is reported and **never licenses the closing "nothing in CI can prove this"**, which only the established answers do; the buckets are therefore ordered by certainty, so a workflow known to be off is reported as off even when its triggers were unreadable, and the *unverified* doubt outranks every trigger-derived answer in both directions (a PR that REMOVES the trigger is a doubt too, not a definitive "cannot be dispatched"). The wording lives in the script, not in the YAML, for #1226's reason — it was composed inline with `jq`, where a text guard cannot catch a false instruction — and the assertions are on **output**: given a workflow with no `workflow_dispatch`, the message does not tell anyone to dispatch it. **A script in a subdirectory used to be invisible, which is the adjacent defect with the OPPOSITE shape — not wrong advice but no advice** (#1979). `SCRIPT_REF` excluded `/` from its tail, so `scripts/lib/stable-tests.ts` was captured as `scripts/lib` — a token no changed path can equal — and the verdict read `none`, *"the diff touches no CI surface at all"*, for a file `update-coverage-summary.yml` lists in its own `paths:`. **Two causes, and the regex was the smaller one.** Widening it is measured rather than assumed — 47 → 51 tokens over the real `.github/`, the five `scripts/lib/**` paths in and the directory token out, which is right because a directory is never a changed FILE. But the YAML only ever spells what it spells, and a shared module is spelled nowhere: of the **24** `scripts/lib/**` files the classifier now reaches, **5 are named** under `.github/` and the other **19 only by import**, so a regex-only fix would have covered a fifth of them. The graph therefore follows imports too — the same indirection `uses:` already gets, one level further in, reusing `impacted-specs-by-import.mjs`'s resolver (its three functions take a path-keyed file map and are root-agnostic; nothing in them was tests-specific) rather than a second copy. The two routes are a **union, not a preference**, and so is the VERDICT: `scripts/lib/stable-tests.ts` is named by one workflow and imported by a script two others run, while `scripts/reconcile-stable-orphans.ts` is reached by the PR lane *and* run by `stable-orphan-reconcile.yml`. Answering with the first route that matched named one workflow and dropped the rest; letting `canary` end the enquiry dropped the dispatch instruction entirely (`advice: null`) — the same rule this file states one level up, *"canary wins over dispatch, and the dispatch advice survives"*, not being applied one level in. That also made `workflowsReaching`'s own promise load-bearing for the first time: it documented excluding the PR lane and did not, so the lane that had just run turned up in the list to dispatch. Measured over all **206** tracked `scripts/` files: **25 leave `none`** (16 → `canary`, 9 → `dispatch`), and the only two moving the other way are the unit tests below. **Know the price before reading a slower PR lane as a regression**: `canary` goes 18 → 35 tracked paths and `dispatch` 49 → 55, and a canary **forces** the `Collect models` sweep, so roughly twice as many CI-only PRs now boot Langflow and walk pre-flight → health gate → Playwright. That is what buying the coverage costs, and it is the thing #1159 asked for. Two traps. The importer walk carries a `seen` set, which is **defensive rather than observed** — the real graph has no cycle today, measured over all 182 source files — because the shape that loops is a cycle among a file's importers that does not pass back through the file, where the `importer === file` skip cannot break it; a first fixture put the start file inside the cycle, which terminates on its own, so the test passed with the guard deleted. The walk also carries a hard **bound**, and that is the part worth keeping: a broken guard does not fail the step, it HANGS it — `node:test`'s own `timeout` cannot preempt a synchronous loop (measured: it does not fire), so the lane reported `0 pass / 0 fail` and burned its budget. The bound turns the same deletion into a named throw, red in under a second. And a **unit test is never CI wiring**, whatever a YAML comment spells: two are named under `.github/` in prose explaining what pins what, so before this a change to either resolved to `dispatch`, contradicting the rule the script states — inert while imports were not followed, and not inert after, since such a file drags its whole import closure in with it (`lib/tmp-dir.mjs`, imported by nothing else, arrived as `dispatch` by exactly that route). A canary run **forces** the `Collect models` sweep, because the gate is `if: needs_models` and would otherwise be skipped by the very run meant to cover it — and neutralises both consequences so a drained key cannot block a CI-only PR: the sweep becomes `continue-on-error` and the credential pre-flight is skipped (#980's trade, #884's check). A verdict the classifier cannot produce fails the step rather than degrading to `skipping`, and a canary spec that no longer exists aborts with exit 2. **Whether the lane needs the provider sweep — and whether it would run a spec bare without one — is a second, separate verdict** (`scripts/provider-dependent-specs.mjs`, #1216), because the inline rule answered only the first and let the second resolve silently to "run it anyway". PR #1152 changed one helper, the import graph correctly pulled in all 7 of its callers, `needs_models` came back `false`, `Collect models` was skipped, and `core-components/agent-component-regression.spec.ts` then ran with no provider and died on `value-dropdown-model_model` — a spec that is `@stable` and green in the daily, so the lane emitted a red that had nothing to do with the diff. The old rule asked *does this spec resolve a model* (area + marker references); the real question is *does it need a provider configured at all*, which the suite's own `@agents` / `@model-provider` tags answer declaratively. The verdict then turns on what the PR is **about**, because forcing the sweep for every provider-dependent spec would re-couple unrelated PRs to key health (`Collect models` is a hard gate here — the #915/#910/#911 cost): a provider-dependent spec **the PR changed itself** forces the sweep and runs, one pulled in because something it **imports** changed is **excluded and announced** (`::warning::` plus the step summary, naming the specs, the reason, and where they *are* covered — #1012's rule). A spec that **consumes** the sweep's output (`models.json`, the resolvers) still forces it either way: those fail at setup without it and have always been in scope, so excluding them would remove coverage that exists today — an asymmetry argued in the script's header rather than left to look like an oversight. `@playground` is deliberately not a provider tag. **"Changed itself" is read from the PR's changed-file list, never from `impacted-specs-by-import.mjs`'s `.direct`** — that field holds every *depth-1 importer*, so on #1152's one-helper diff all 7 callers were `direct`, and reading it as "the PR changed this" forced the sweep for precisely the case the fix exists for. It survived a hand-built fixture (`direct: []`) the real resolver never emits, which is why the unit lane now feeds the verdict the **resolver's actual output** on that diff. **Excluding *every* selected spec forces the sweep instead**: decoupling from key health is worth one spec's coverage, never worth all of it, since an empty run list skips the E2E job and a lane that runs nothing is no evidence at all. The re-derivation of the run list is also **skipped on a canary run** — a canary's specs come from `ci-change-coverage.mjs`, not the import graph, so overwriting them with the (empty) verdict list would blank `$SPECS`, trip `has_specs=false` and skip the job together with `Collect models` and the health gate, reopening #1159's hole. Both are pinned structurally. When the exclusion empties the run list the job's own `has_specs` gate skips the E2E run, which is the only safe outcome (`npx playwright test` with no paths runs the whole suite) and honest only because the warning always accompanies it. One behaviour tightens on the way: the old inline loop used `grep -q … 2>/dev/null`, so a spec it could not read counted as "no match"; the verdict now treats an unreadable spec as **undecidable** and fails the step, because defaulting to LLM-free there is how a provider-dependent spec would run bare again. The run list is emitted to `$GITHUB_OUTPUT` exactly once, after the verdict re-derives it — pinned by a structural test, since an early second write would leave which value wins up to the runner and let an excluded spec reach Playwright anyway. **The run summary is rendered by `scripts/render-impacted-summary.mjs`, not by inline shell** (#1226). Three wrong figures shipped out of that block while it lived in the YAML, each with every gate green: `running in this PR` was `TOTAL - DROPPED`, so a provider-excluded spec counted as executed; the same line read `0` on a **canary** run, where `TOTAL` is 0 by definition while three specs do run; and the `@stable` tally beside it was the resolver's `stableSelected`, scoped to `selected` (post-cap) while the total was `.specs` (pre-cap), so the pair read as one breakdown of two different sets (a `get-auth-token.ts` diff printed `178 … @stable: 20`, where the true figure for 178 is 155). Each fix added another regex over the workflow text, and each of those regexes was then shown to miss its own mutation — swapping the printed `$RUN_COUNT` for `$TOTAL`, or hoisting the caveats above the counts, both passed. **A guard that pins a spelling does not pin a behaviour**, which is why the rendering moved to a script whose tests assert on output: given a verdict that excluded one spec, the summary says 6, and says it above the caveats. Three things it now guarantees. The run count is the length of the list handed to Playwright, passed in as `--specs` and never recomputed. The counts come **first** — appending caveats as they occurred put the cap's dropped list (217 bullets on a suite-wide change) above the figure a reviewer opens the summary for, which answered #1226 in letter only. And a verdict that aborts **degrades instead of erasing**: the resolution line and the caveats still establishable are printed with the gap named, where the buffered version it replaced left a 0-byte summary. The `@stable` tally comes from the verdict's `stableRun`, counted over the surviving run list inside `provider-dependent-specs.mjs` (which already reads every selected spec's source, so this costs no `grep` in the YAML), is **omitted** on a canary run where the verdict never saw those specs, and reads `@stable` from a `tag:` array rather than anywhere in the file — the loose substring test overcounted 8 of 235 specs, one of whose only occurrence is the comment "`@release`, never `@stable`". The strict predicate yields 170 files, matching what `scripts/stable-tests.ts` derives from the spec ASTs. The `::warning::` annotations stay inline in the workflow: they are log-level, unaffected by ordering, and they are what still tells a reviewer the run was shortened if the step dies before it can render. **A provider-health skip no longer reads as coverage** (#1456): the impacted-specs run emits `--reporter=github,json` (the CLI list REPLACES the config's, so this lane wrote no machine-readable report at all) and `scripts/lane-coverage-verdict.mjs` then headlines the run summary with what went unverified, and FAILS the job when the report is unreadable, or when a provider-health skip fired **and** the recorded account was dry (or, for a run that covered nothing, not demonstrably alive) (#1800 — failing on "zero tests executed" alone reddened a PR whose selection was one wholly-gated spec) — see the coverage-verdict bullet below.
- **CLAUDE.md size budget** (`npm run check:claude-md-budget`, `scripts/check-claude-md-budget.mjs`, #2542) — a step of the TypeScript check job, run before the unit lanes; it and they carry `if: ${{ !cancelled() }}`, so a red `tsc`, budget or unit lane never hides the others' verdicts. Every tracked `CLAUDE.md` gets a byte budget (40,000 for the project-root guides, 20,000 for area guides) and every block in it one of 3,000. A block starts after a blank line or at a column-0 list marker or heading, and everything indented stays with it — deliberately not a Markdown parse: two review rounds on a hand-written CommonMark splitter each found boundaries that moved on a nested table, an indented heading or a CRLF fence. An `@path` import fails outright, because it inlines a file the budget never sees. Tokens are read as Claude Code reads them (cut at `#`, `\ ` unescaped); `~/` and absolute paths fail by syntax alone (CI never holds them, a laptop may), and so does any `.md` path; any other token fails only when it names a file next to the guide, so `@stable` and `@axe-core/playwright` pass. A breach names the file, the largest blocks and the fix: the narrative goes to `docs/infra/<mechanism>.md`, the guide keeps the rule plus a link. Raising a budget is an edit to `BUDGETS` in the script.

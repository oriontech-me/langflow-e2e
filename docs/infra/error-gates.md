# Error gates in `tests/fixtures/fixtures.ts`

> Moved verbatim from `CLAUDE.md` (#2532). `CLAUDE.md` keeps the standing rules and links here; this file keeps the mechanism, its history and its measurements. Counts and dates are as of when each passage was written. Re-measure before quoting one.

- **`tests/fixtures/fixtures.ts`** — Always import `test` from here, never directly from Playwright. It extends the base `test` with backend HTTP error monitoring and flow execution error detection. **The two are not equally strong, and the difference decides how much a green run is worth (#1084):** a `flow_error` **fails** the test; an `http_error` is **logged and never fails it**, on any path, for any endpoint — so the only thing between a real backend 500 and a green test is a human reading the log (checklist step 4 below, `CONTRIBUTING.md` step 5). Which responses reach that log is decided by `tests/fixtures/http-error-policy.ts` — every 4xx/5xx on an `/api/` route except the documented exemptions (auth endpoints; the external Langflow Store, unreachable in CI). It genuinely covers 4xx/5xx now; before #1084 it matched four exact codes and silently missed 401/403/405/409/502/503, which is why `execution-error-notification` could mock a 503 specifically to slip past it. Escape hatches: `page.allowFlowErrors()` for tests that provoke execution failures, `page.allowHttpErrors()` for tests that drive an endpoint into a 4xx/5xx on purpose (keeps the advisory log trustworthy). `PW_HTTP_ERROR_DEBUG=1` prints what the policy ignored, with reasons. **A third hatch exists because the other two are both wrong for a spec that merely *passes through* a state where a filed product defect fires** (#1008): `page.expectKnownHttpError({ pathname, status, reason })` quietens **only** that exact status-plus-pathname — reported as `📌 Known backend defect`, never as `🚨 Backend Error`, which is the string the deterministic pipeline's VALIDATE gate greps for. The motivating case shows why neither alternative fits: `folder-deletion-integrity.spec.ts`'s `@destructive` test has to reach the zero-project state, where the frontend fired `GET /api/v1/projects/undefined` and the backend correctly answered `422` (LE-2231 — fixed upstream and verified on `1.13.0.dev14` by this very declaration going stale, so #1008 turned it into an assertion that the request is never sent) — while its own body deletes N projects through the UI, where `DELETE /api/v1/projects/{id}` → 500 with the toast still reading "deleted successfully" is a *separate* filed defect (#965/LE-2020) that this loop is unusually well placed to catch. `allowHttpErrors()` would have traded one known error for blindness to the other; an `IGNORED` entry would have hidden it from all 235 specs and forever. **The declaration is verified in both directions, and that is the load-bearing half:** a declared defect that does **not** fire **fails the test**, naming the call to delete and the issue to close — because an exemption whose justification expired silently is the failure #1084 was raised about, and a printed warning would be one more line nobody reads (the `mode=count` lesson). Consulted **last**, after the `/api/` test and after `IGNORED`, so a declaration can only ever quieten what the policy would have reported — never widen monitoring onto an asset or un-ignore a global exemption. Covered by `npm run test:units` for the matching plus the behavioural `tests/fixtures/http-error-gate.spec.ts` for the fixture half; the stale-declaration branch is reachable from a test only because it keys on `testInfo.status === "passed"` rather than `expectedStatus`, which lets `test.fail()` assert it — the exact assertion `flow-error-gate.spec.ts` had to record as a follow-up for its own mid-test interrupt. **Which run-stream responses count as a `flow_error` is decided by `tests/fixtures/flow-error-policy.ts`** (#1162, covered by `npm run test:units` plus the behavioural `tests/fixtures/flow-error-gate.spec.ts`), and on 1.12.x that detection was **dead for every playground/agent/node run**: the run is `POST /api/v2/workflows`, which the inline URL list (`/build/`, `/run/`, `/events?event_delivery=`) did not match, served as `text/event-stream`, which the inline detector skipped wholesale — so an Anthropic 400 reached the UI with no verdict at all, and `page.allowFlowErrors()` was a no-op on that path for the 13 specs that call it. **Both surfaces now fail the test** (#1165): `runStreamSurface()` returns `v1` for the endpoints the fixture always watched and `v2` for `POST /api/v2/workflows`, and a verdict on either fails. v2 shipped **staged** — computed and logged as ADVISORY — and was flipped only after the audit below. **v1 is not "unchanged", and reading it that way will mis-triage the first red it produces:** the old detector skipped by *content type* before it looked at the URL, so a v1 `text/event-stream` or `application/x-ndjson` body was never classified, and the `{"event": "error"}` envelope never matched — all three now fail the test. That is the same dead-gate flip this staging argues against, allowed only because `/api/v1/build/{id}/flow` has been retired since 1.11 (see `ui-ux/execution-error-notification.spec.ts`), so it is latent on every scheduled lane and live only for a supervised `manual.yml` dispatch at ≤ 1.10; staging v1 too would leave the suite with no failing flow-error gate at all. Turning the new half straight to failing is not a no-op: 88 specs trigger a run and 75 have no hatch, and some provoke an execution error on purpose (`core-components/validate-raise-errors-components.spec.ts` raises a `ValueError` from a custom component, asserts the error UI, and is `@stable @release`). So step 1 made the cause visible — all #1059 needed — and step 2 flipped v2 to failing, the same order #1084 used for the HTTP half. **The count that justified staging was the wrong unit, and the audit is the useful part to carry:** "75 unhatched" is how many specs *could* emit, while the advisory log across five consecutive scheduled dailies named **ten** distinct causes — eight of them specs provoking an error deliberately that already carried the hatch, plus `flow-error-gate.spec.ts` itself, the largest single emitter, which mocks a `RUN_ERROR` on purpose. **The other two were the finding, and they are why the policy now knows a provider outage from a flow error:** a Google embedding quota (`RESOURCE_EXHAUSTED`) and a drained Anthropic key (`credit balance is too low`), delivered *inside the run stream* on specs with no hatch. Failing on those is not one red test — the fixture's failure text matches nothing in `scripts/lib/infra-signature-patterns.json`, which is transport-level only, so `remove-stable-from-failures.ts` would score an empty account as attributable and strip `@stable` in an unreviewed commit, on a repo with four recorded account drains (#772 and #1450 openai, #1029 google, #1169 anthropic). `PROVIDER_OUTAGE_PATTERNS` therefore downgrades those to **unevaluated** — reported with their message and shape, never as clean (#1012) — and every one of `classifyFlowError`'s eight return sites funnels through one helper so the downgrade cannot be added to the sampled shapes and forgotten on the rest. **Within that scope the patterns err wide, and the reason is an asymmetry rather than a preference:** too wide costs one unevaluated run, too narrow costs a tag, so the first version's one-token-per-provider list was measured against the real payloads and missed three wordings this repo already recognises elsewhere (`no credits remaining`, `billing_not_active`, a bare 402 — all three in `openai-compatible-provider-setup.spec.ts:1029`, which is one of the two specs the carve-out was built for). Two traps behind that. The match runs on the message **after** `summarize()` cuts it to 3 lines / 400 chars, so a pattern anchored on a payload's trailing token — OpenAI states its quota twice, in prose at ~offset 50 and as `'type': 'insufficient_quota'` at ~offset 276 — is one long component name from being unreachable; hence `\bquota\b`, pinned by a test that pads the prefix until the tail token is gone. And `run-node-and-wait.ts`'s `TRANSIENT_PATTERNS` classifies the **same** run message for its retry decision, so the two lists have to agree about a string or the next gap opens where they diverge. The instrument mattered as much as the result: #1165 asked for a full-suite `manual.yml` dispatch, which that lane cannot finish **at any cap** (#1174 — raising it 90 → 180 does not help: 32 of the 298 specs are lane-gated and unreachable there at all), while the daily prints the same block every weekday, its **job logs outlive the 7-day artifact retention**, and it is sharded — so a cause narrows to one shard's 52 specs before any content matching, which is what settled the rows the earlier inventory had to leave as "strong, not proof". The policy matches the v2 shapes (`type: "RUN_ERROR"`, `event_type: "error"` incl. its minimal `{error: "…"}` payload, a node `status: "error"` carrying `errorMessage`) alongside the v1 ones (plus the v1 `{"event": "error"}` envelope, which neither old shape covered), parses SSE and NDJSON alike, anchors URL matching on the **pathname** (`url.includes("/build/")` matched `/assets/build/index.js`), excludes the `/api/v2/workflows/pending` 5 s poll, and applies the raw-text traceback patterns **only to a body that is not a structured stream** — over a real stream they scan every assistant token and echoed prompt, so an agent explaining a `TypeError` would fail a healthy run. **The two surfaces reach a verdict by different routes, and that is the point of #1168:** v1 still asks for the buffered body (`response.text()`, 2 s), while **v2 is captured as it arrives** by `tests/fixtures/run-stream-capture.ts` (CDP `Network.streamResourceContent`). Asking after the fact cannot work on v2 — `response.text()` does not read a stream, it asks Chromium for a buffer, and a run stream routinely outlives its test: the UI shows the error, the spec asserts and ends, the request is cancelled and the partial buffer is discarded, so the ask fails with `Protocol error (Network.getResponseBody): No resource with given identifier found`. Measured on `validate-raise-errors-components.spec.ts` at 1.12.0.dev10: **no verdict at all, 3 runs out of 3**, on a run that did emit `event_type=error` — and raising the teardown drain 3 s → 10 s changed nothing, because the body is not slow, it is gone. With the capture it is 5 runs out of 5. **A cancelled stream still yields every byte that arrived, and a partial body is enough** — `parseStreamEvents()` tolerates a truncated tail and the error event lands long before the stream closes. `page.route` + `route.fetch()` was rejected as the tee: `APIResponse` has no streaming body accessor, so the fixture would buffer the whole run before fulfilling and break incremental delivery for every playground spec. **Every path that gives up without a verdict is counted and printed** — an unevaluated stream is unknown, not clean (#1012's rule), the newest of them being the residual `settle()` could not drain at teardown, which the capped drain #1452 introduced would otherwise have dropped in silence — **and since #1452 a spec can read that accounting** through `page.flowErrorReport()` (`tests/fixtures/flow-error-report.ts`, unit-tested; seven states pinned behaviourally in `flow-error-gate.spec.ts`). It exists because the gate can only fail on a verdict it *reached*, while four spec docs asserted that gate and one of them — `agent-tool-error-handling` — cited it as its whole "the run did not crash" criterion — a run the fixture could not read leaves those green with the assertion silently not happening. `report.clean` is true only when every run stream in the test was evaluated and none failed, **and** the v2 surface was watched at all — that last clause is the load-bearing one mid-test, since with no CDP session the unevaluated count stays empty until teardown and is therefore no signal at the moment a spec asks. A stream still open is `pending`, which is not clean either, and it deliberately does not wait for one. Read-only and not a hatch: `allowFlowErrors()` suppresses the gate, never the report, so a hatched spec can still find out what happened — but the report is **cumulative for the whole test, not per run**: once anything has failed, `clean` stays false, and a first draft of both this entry and `CONTRIBUTING.md` promised the opposite (that a spec could tolerate one deliberate failure and then assert a *later* run came back clean). A per-run window is two reports diffed, which is what the JSDoc shows. **A caller must assert `evaluated > 0` alongside `clean`**, for the reason the accessor exists at all: `clean` is vacuously true when nothing was accounted for, so on its own it makes "the run was healthy" and "the send never fired" the same assertion — measured, the healthy-run behavioural test passed under every mutation it was meant to catch until `evaluated` was asserted. The `settle()` it does first is load-bearing and measured, not defensive — removed, **three of the seven** behavioural tests fail 5 runs out of 5 (two reporting a **failed** run as clean and one reporting a healthy run as unaccounted; an earlier version of this sentence said "two of the four", stale in both numbers), because `judgeCapturedStream` runs from an async continuation and an accessor that answers first reports exactly what it exists to prevent. Two traps worth knowing: the error event's message object carries `"error": false`, so the old `data.error === true` check read a failed run as healthy; and attaching any `.catch()` to the **v1** body-read promise marks its rejection handled, which silently downgrades the gate from "interrupts the running test" (measured 238 ms) to "fails its teardown" (10 249 ms) — hence that read is tracked nowhere at all, pinned by a unit assertion.

- **An HTTP error's body: read, empty, or never obtained (#1432)** — the monitor recorded every 4xx/5xx and then tried to attach its body; when `response.text()` threw, the string `"Could not read response"` went into the entry and **nothing was printed**. The log showed the `🚨 Backend Error` line and moved on, indistinguishable from an error whose body was empty, with the reason discarded along with the body — #1012's rule broken in the fixture that is itself the suite's evidence trail. **The measurement is the part worth carrying, because it inverted how exotic that branch looked: on Playwright 1.58.2 (Chromium 145) Chromium did not retain a zero-length response body**, so `response.text()` *rejected* with `response.text: Protocol error (Network.getResponseBody): No data found for resource with given identifier` rather than resolving to `""` — the silent branch was not an edge case, it was what every bodyless response **the page never read itself** did. That scope is measured, not decorative (#2167's review): on 1.58.2 a page that read the body (`fetch(u).then(r => r.text())`) made the same bodyless `400` resolve to `""`, so a spec whose frontend reads its own responses — which is how Langflow's does — may already have printed `<empty body>` there; what the bump certainly moved is a response nobody on the page read, the gate's own probe among them. Measured across 200 / 204 / 400 / 404 / 500, with an explicit `content-length: 0` and for a gzip of the empty string; a redirect gives a third real message (`Response body is unavailable for redirect responses`). **On Playwright 1.65.1 (Chromium 159, #2167) every one of those bodyless cases resolves to `""`** and prints `<empty body>`; what still rejects, on both versions, is a body cut off mid-transfer (headers sent, connection dropped — the same `No data found` message), a response whose page navigated away before the read (`No resource with given identifier found`), and the redirect. **The `<empty body>` branch is a different observation from the unread one**: the body was read and was empty (now a bodyless response, and on every version a non-zero-LENGTH body that decodes to the empty STRING, such as a bare UTF-8 BOM), against a body never obtained. `http-error-gate.spec.ts` pins all three on the real transport: a truncated `400` for the unread branch, and a bodyless `400` and a BOM body for the empty one. The bodyless test is the one that would notice Chromium changing back — and the bump to 1.65.1 is how this was found: the gate's old probe for the unread branch WAS the bodyless `400`, and it went red. The status matrix, the explicit `content-length: 0` and the gzip remain one-off measurements nothing re-runs. **What this is NOT is an explanation of #1424, and an earlier draft of this entry said it was — the correction is the useful half:** #1424 is **closed** (root-caused 2026-08-12, fixed by PR #1441), **two of its four `400`s did carry bodies**, a 2026-07-13 occurrence on the same endpoint printed `{"detail":"Invalid API key for OpenAI"}` in full, and the real causes were a create-vs-update race (#1431), a key with no credits, and an Azure endpoint answering past its 10 s validation timeout. The justification is #1424's own close-out instead — *"it is the reason this took three dailies"* — which is a cost this removes without needing to have been the cause. `tests/fixtures/http-error-body.ts` now decides what is recorded and what is printed: **every** branch prints, the reason is the first NON-BLANK line of the thrown value (capped, and tolerant of a non-`Error` throw, since the catch it replaces accepted anything). **Tolerant has two halves and the second one is the trap:** `Error.message` is TYPED `string` and is a plain own property, so a thrown object can carry a `Symbol`, a number or an object there — and the coercion happened one frame above the try, where `raw.split()` threw `TypeError: raw.split is not a function` out of an async `response` handler that has no surrounding try. An unhandled rejection there FAILS the test, which is precisely what #1084 says an HTTP error never does, so the helper that exists to keep the evidence trail honest would have been the one thing in it able to redden a run, and the entry carries `responseBody` **or** `bodyUnavailable` and never both — two optional fields rather than one sentinel string, because a sentinel is also a value a backend can legitimately return. **Three states, not two:** the entry is recorded BEFORE the read (deliberately — the read is an `await` in an async handler that teardown does not wait for, #1084's undercount), so a read that never settles is stamped with a pending reason up front and overwritten by whichever outcome wins; the teardown summary then groups the bodies that never arrived by reason, which is what makes a `🚨` line with no `Response:` line under it visible instead of looking like a body nobody bothered to print. Covered by `npm run test:units` (`http-error-body.test.ts`, the printing decision) plus `http-error-gate.spec.ts` (the wiring, on the real transport).

# Agent playground — a math prompt reaches the run exactly once

**Last validated:** Langflow 1.12.x

---

## What this test validates *(required)*

A regression guard for input duplication between the Playground input box and the
Agent run. Sending `2+2` to a Simple Agent must arrive as `2+2` — not `2+22+2`,
not `22+2` — and come back as `4`, not `26`.

The duplication is a **frontend** fault — the typed text entering the run twice —
so it shows in two places at once: the user's own chat message carries the
doubled string, and the answer becomes the arithmetic of the doubled expression
(`2+22+2` = 26) instead of `4`. Both are asserted, because either alone is
weaker: a reply of `4` does not prove the input was clean, and a clean-looking
input does not prove the run used it.

If this fails, either a user's prompt is being mangled on its way to a tool, or
the Agent no longer executes at all (see the Notes on #1465).

---

## Tags *(required)*

`@release` `@components` `@workspace`

`@stable` is **not** set. That is the tag that decides whether `daily-stable.yml`
runs it, and its absence is why this spec sat broken on `main` with no signal
(#1465) — a call the issue asks to revisit once it is green on several
`--retries=0` runs.

## Preconditions *(optional)*

- Langflow running at `PLAYWRIGHT_BASE_URL`.
- `ANTHROPIC_API_KEY` set and **funded**: the test gates on the health
  `collect-models` recorded in `providers.json` (`providerSkipGate("anthropic")`),
  so a drained key skips with the collected reason instead of blocking the
  backend past gunicorn's 300 s timeout (#1029).
- `models.json` / `providers.json` generated by
  `npx playwright test tests/collect-models.spec.ts`.
- Run with `--workers=1` — the spec loads a named template (agent-family
  convention).
- The instance does **not** need Anthropic pre-configured: the load configures it
  through the Agent node. Both states are exercised in practice (CI arrives
  configured via `Collect models`; a fresh container does not), and they take
  different entry points into the provider panel — see Notes.

## Step by step *(required)*

1. Load the **Simple Agent** template through `SimpleAgentTemplatePage`, pinned to
   a Claude model from the collected catalog. The Page Object configures the
   provider and then blocks until the Agent's PERSISTED binding carries that
   provider and model (#751/#1274) — a run that starts before it does reaches the
   backend with no model and fails as `ComponentBuildError: No model selected`.
3. Open the Playground and send `2+2`.
4. Wait for the assistant message of the completed run.
5. Assert the user message text and the assistant message text.
6. Delete the flow the run created (id-scoped, in `afterEach`).

---

## Validation criterion *(required)*

Read from the Playground's chat messages, whose testid embeds the message text
(`chat-message-<sender>-<text>`):

- the user message reads **exactly** `2+2` — a duplicated input renders
  `2+22+2` (or `22+2`) and fails;
- the assistant message reads **exactly** `4` — the arithmetic of a duplicated
  input is `26`, which is asserted against by name so a duplicated run cannot
  pass by producing a plausible-looking answer.

Reaching an assistant message at all is part of the criterion: it only exists
once the run completed, so a run that errors (no model bound, provider failure)
cannot reach the assertions.

**Why not the tool payload.** Until 1.12 this spec expanded the message's
execution header (`header-icon` → `icon-Check`) and read the tool's JSON blocks
(`chat-code-tab`). Measured on `1.12.0.dev26`, both are gone — `header-icon` and
`chat-code-tab` count **0** — which is the same 1.11→1.12 change that removed
the expandable tool accordion (#827). Reading the payload off the run stream was
considered and rejected: for `2+2` the Agent answers directly without calling the
Calculator, so an assertion anchored on a tool call would depend on the model
*choosing* to use one (#1187's lesson). The chat messages carry the duplication
signature unconditionally.

## Guarding against false positives *(how)*

- The negative assertions are the point: a passing run must produce `4` **and**
  not the duplicated arithmetic. A test that only checked "a reply arrived"
  would pass on the very bug this exists for.
- The completion gate is a real observable of the finished run, not a fixed
  wait — an unfinished or errored run produces no assistant message and fails.
- The provider setup must be **verified**, not assumed: a helper that returns
  having configured nothing is how this spec failed for weeks (#1465). Two things
  now prevent it — the shared entry point fails loudly when it cannot reach the
  panel, and the Page Object blocks on the persisted binding rather than on the
  helper returning.
- Force-failure (CONTRIBUTING §2) is run during VERIFY.

## Notes *(optional)*

- **Why it was red on `main` (#1465).** On `1.12.0.dev26` the Agent node's
  Setup Provider control carries
  `aria-labelledby="node-Agent-<id>-field-model-label"`, so its **accessible name
  is "Language Model required"**, not "Setup Provider". Measured live:

  ```
  aria snapshot:  - button "Language Model required": Setup Provider
  role=button, name "Setup Provider"  → 0 matches
  button filtered by text              → 1 match
  ```

  The three provider helpers looked the control up as
  `getByRole("button", { name: "Setup Provider" })`, so on an instance where the
  provider is **not** configured they matched neither entry point and returned
  through their `"No Agent node found on canvas — skipping…"` branch, doing
  nothing. The Agent then ran with no model and the backend answered
  `ComponentBuildError: Error building Component Agent: No model selected.`,
  which surfaces as the completion gate timing out 30 s later.

  Two properties made it invisible: the helper's early return is silent (the same
  class of defect as #1461 — a single negative observation reported as a
  conclusion), and this spec carries no `@stable`, so no scheduled lane runs it.
  It only ran again when a PR touched a helper it imports.

- **The spec had no mirrored doc until #1465.** It was authored as a bug-repro
  spec; the missing doc is why the premise it depends on (a `role=button` named
  "Setup Provider") was never written down anywhere a reviewer could check.

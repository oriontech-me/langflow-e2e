## Project Overview

This is an independent end-to-end regression test suite for [Langflow](https://github.com/langflow-ai/langflow), built with Playwright and TypeScript. It tests any running Langflow instance via URL — it is fully decoupled from Langflow's source code.

## Environment Setup

Copy `.env.example` to `.env` and configure:

```
PLAYWRIGHT_BASE_URL=http://localhost:7860/
LANGFLOW_SUPERUSER=langflow
LANGFLOW_SUPERUSER_PASSWORD=langflow123
OPENAI_API_KEY=
ANTHROPIC_API_KEY=
```

Start a Langflow instance before running tests:

```bash
./scripts/start-langflow-docker.sh           # Docker — nightly (langflowai/langflow-nightly:latest)
./scripts/start-langflow-docker.sh 1.5.1     # Docker — a released version (langflowai/langflow)
LANGFLOW_IMAGE=langflowai/langflow:latest ./scripts/start-langflow-docker.sh   # any exact image
./scripts/start-langflow-pip.sh              # Via pip (local dev)
./scripts/stop-langflow-docker.sh            # Stop Docker instance
```

## What to work on

`ROADMAP.md` is the source of truth for **direction and order** — it schedules the
decided backlog into 2-week waves. Each dated wave is a GitHub milestone named after
its `### Wave N — Axis` heading; its work items are the issues labeled `roadmap`
assigned to it. Before picking up work, take an open issue from the current wave:

```bash
gh issue list --label roadmap --milestone "Wave N — Axis"
```

Off-wave work is allowed **only** when it traces to an approved exception issue: a
follow-up, a `daily-failure` triage issue, or a `community`-labeled regression
(worked in severity order — `high` → `medium` → `low priority` — when indicated;
see `ROADMAP.md` → *Intake*). No exception issue ⇒ it belongs to the current wave.

Do not restate the current wave here — it changes every cycle; follow the pointer.

## Architecture

### Test Infrastructure

- **`tests/fixtures/fixtures.ts`** — Always import `test` from here, never directly from Playwright. It extends the base `test` with backend HTTP error monitoring and flow execution error detection. **The two are not equally strong, and the difference decides how much a green run is worth (#1084):** a `flow_error` **fails** the test; an `http_error` is **logged and never fails it**, on any path, for any endpoint — so the only thing between a real backend 500 and a green test is a human reading the log (checklist step 4 below, `CONTRIBUTING.md` step 5). Which responses reach that log is decided by `tests/fixtures/http-error-policy.ts` — every 4xx/5xx on an `/api/` route except the documented exemptions (auth endpoints; the external Langflow Store, unreachable in CI). It genuinely covers 4xx/5xx now; before #1084 it matched four exact codes and silently missed 401/403/405/409/502/503, which is why `execution-error-notification` could mock a 503 specifically to slip past it. Escape hatches: `page.allowFlowErrors()` for tests that provoke execution failures, `page.allowHttpErrors()` for tests that drive an endpoint into a 4xx/5xx on purpose (keeps the advisory log trustworthy). `PW_HTTP_ERROR_DEBUG=1` prints what the policy ignored, with reasons. **A third hatch exists because the other two are both wrong for a spec that merely *passes through* a state where a filed product defect fires** (#1008): `page.expectKnownHttpError({ pathname, status, reason })` quietens **only** that exact status-plus-pathname — reported as `📌 Known backend defect`, never as `🚨 Backend Error`, which is the string the deterministic pipeline's VALIDATE gate greps for. The motivating case shows why neither alternative fits: `folder-deletion-integrity.spec.ts`'s `@destructive` test has to reach the zero-project state, where the frontend fires `GET /api/v1/projects/undefined` and the backend correctly answers `422` — while its own body deletes N projects through the UI, where `DELETE /api/v1/projects/{id}` → 500 with the toast still reading "deleted successfully" is a *separate* filed defect (#965/LE-2020) that this loop is unusually well placed to catch. `allowHttpErrors()` would have traded one known error for blindness to the other; an `IGNORED` entry would have hidden it from all 235 specs and forever. **The declaration is verified in both directions, and that is the load-bearing half:** a declared defect that does **not** fire **fails the test**, naming the call to delete and the issue to close — because an exemption whose justification expired silently is the failure #1084 was raised about, and a printed warning would be one more line nobody reads (the `mode=count` lesson). Consulted **last**, after the `/api/` test and after `IGNORED`, so a declaration can only ever quieten what the policy would have reported — never widen monitoring onto an asset or un-ignore a global exemption. Covered by `npm run test:units` for the matching plus the behavioural `tests/fixtures/http-error-gate.spec.ts` for the fixture half; the stale-declaration branch is reachable from a test only because it keys on `testInfo.status === "passed"` rather than `expectedStatus`, which lets `test.fail()` assert it — the exact assertion `flow-error-gate.spec.ts` had to record as a follow-up for its own mid-test interrupt. **Which run-stream responses count as a `flow_error` is decided by `tests/fixtures/flow-error-policy.ts`** (#1162, covered by `npm run test:units` plus the behavioural `tests/fixtures/flow-error-gate.spec.ts`), and on 1.12.x that detection was **dead for every playground/agent/node run**: the run is `POST /api/v2/workflows`, which the inline URL list (`/build/`, `/run/`, `/events?event_delivery=`) did not match, served as `text/event-stream`, which the inline detector skipped wholesale — so an Anthropic 400 reached the UI with no verdict at all, and `page.allowFlowErrors()` was a no-op on that path for the 13 specs that call it. **The verdict's strength now depends on the surface, and that staging is deliberate:** `runStreamSurface()` returns `v1` for the endpoints the fixture always watched — those keep **failing** the test — and `v2` for the new one, where a verdict is **logged as ADVISORY and does not fail**. **v1 is not "unchanged", and reading it that way will mis-triage the first red it produces:** the old detector skipped by *content type* before it looked at the URL, so a v1 `text/event-stream` or `application/x-ndjson` body was never classified, and the `{"event": "error"}` envelope never matched — all three now fail the test. That is the same dead-gate flip this staging argues against, allowed only because `/api/v1/build/{id}/flow` has been retired since 1.11 (see `ui-ux/execution-error-notification.spec.ts`), so it is latent on every scheduled lane and live only for a supervised `manual.yml` dispatch at ≤ 1.10; staging v1 too would leave the suite with no failing flow-error gate at all. Turning the new half straight to failing is not a no-op: 88 specs trigger a run and 75 have no hatch, and some provoke an execution error on purpose (`core-components/validate-raise-errors-components.spec.ts` raises a `ValueError` from a custom component, asserts the error UI, and is `@stable @release`). So step 1 makes the cause visible — all #1059 needed — and step 2 flips v2 to failing after auditing and hatching those specs, the same order #1084 used for the HTTP half. The policy matches the v2 shapes (`type: "RUN_ERROR"`, `event_type: "error"` incl. its minimal `{error: "…"}` payload, a node `status: "error"` carrying `errorMessage`) alongside the v1 ones (plus the v1 `{"event": "error"}` envelope, which neither old shape covered), parses SSE and NDJSON alike, anchors URL matching on the **pathname** (`url.includes("/build/")` matched `/assets/build/index.js`), excludes the `/api/v2/workflows/pending` 5 s poll, and applies the raw-text traceback patterns **only to a body that is not a structured stream** — over a real stream they scan every assistant token and echoed prompt, so an agent explaining a `TypeError` would fail a healthy run. **The two surfaces reach a verdict by different routes, and that is the point of #1168:** v1 still asks for the buffered body (`response.text()`, 2 s), while **v2 is captured as it arrives** by `tests/fixtures/run-stream-capture.ts` (CDP `Network.streamResourceContent`). Asking after the fact cannot work on v2 — `response.text()` does not read a stream, it asks Chromium for a buffer, and a run stream routinely outlives its test: the UI shows the error, the spec asserts and ends, the request is cancelled and the partial buffer is discarded, so the ask fails with `Protocol error (Network.getResponseBody): No resource with given identifier found`. Measured on `validate-raise-errors-components.spec.ts` at 1.12.0.dev10: **no verdict at all, 3 runs out of 3**, on a run that did emit `event_type=error` — and raising the teardown drain 3 s → 10 s changed nothing, because the body is not slow, it is gone. With the capture it is 5 runs out of 5. **A cancelled stream still yields every byte that arrived, and a partial body is enough** — `parseStreamEvents()` tolerates a truncated tail and the error event lands long before the stream closes. `page.route` + `route.fetch()` was rejected as the tee: `APIResponse` has no streaming body accessor, so the fixture would buffer the whole run before fulfilling and break incremental delivery for every playground spec. **Every path that gives up without a verdict is counted and printed** — an unevaluated stream is unknown, not clean (#1012's rule). Two traps worth knowing: the error event's message object carries `"error": false`, so the old `data.error === true` check read a failed run as healthy; and attaching any `.catch()` to the **v1** body-read promise marks its rejection handled, which silently downgrades the gate from "interrupts the running test" (measured 238 ms) to "fails its teardown" (10 249 ms) — hence that read is tracked nowhere at all, pinned by a unit assertion.

- **Component availability is a packaging decision, per image (#1040)** — `docs/component-distribution-policy.md` is the standing answer, so it stops being re-decided per incident (it was decided wrongly twice: #898 and #907 were both attributed to missing `langchain-*` extras when the 1.12 packaging split was at least as much the cause; #1039 corrected the record and demoted the Groq/Mistral specs). Most families moved out of `lfx.components.*` into per-vendor distributions plus an aggregate `lfx-bundles` the nightly does **not** install; the old paths are shims deleted at **M4**, which has no published date anywhere — not in `BUNDLE_API.md`, not in upstream issues/PRs, and `langflow-ai/langflow` has no milestones (searched, not assumed). Measured on the image `1.12.0.dev10` for what is installed (21 `lfx-*` distributions, no `lfx-bundles`) and **36** categories / **189** component types in `GET /api/v1/all`; and on `origin/release-1.12.0` — the line the nightly is cut from, **not `main`** — for the tree: **106** `lfx/components/*` directories, **79** shims (77 `lfx-bundles-shim` + 2 `lfx-compat-shim`), **27** core. `main` reads 78/28 because `cassandra` became a shim on the release line only (2026-07-30, not merged back), so the ref is part of the measurement — the first version of this entry recorded main's split against a nightly. The load-bearing rule holds in **one** direction: **no category appears for a family the image does not ship** (every shim with a category has its distribution installed, 10 of 10; the other 69 have none). The biconditional is false — 11 of the 27 core directories produce no category at all, and three installed distributions have none of their own (`lfx_datastax` supplies two, `lfx_vllm` and `lfx_openai_compatible` ship no components) — so a directory count never predicts a catalog. Two shim flavours, and the difference changes the diagnosis: a `lfx-bundles-shim` family really moved and raises `ModuleNotFoundError` naming its distribution, while a `lfx-compat-shim` is an internal rename alias (`knowledge_bases` → `files_and_knowledge`) with no distribution and no error at all — checking whether a package is installed answers nothing for it. **The source tree and the catalog do not correspond 1:1, and reading the tree to answer an availability question will mislead you**: `knowledge_bases` is a *shim* directory while the `Knowledge` component is present under the **`files_and_knowledge`** category. Installed also ≠ buildable — with `lfx-bundles` present but `langchain-groq` missing the component is placeable and fails at run time, which is why `probe-component-available.ts` (presence) and `probe-component-buildable.ts` (#900, builds) both exist. **`globalSetup` reports catalog drift** against the committed baseline `tests/assets/catalog/component-catalog-baseline.json` on every run (one request, 70–85 ms / 524 KB), so a vanished family is named at the gate instead of surfacing as a `waitForSelector` timeout 30 s into a spec (#884's misclassification tax). It snapshots `category -> component types` rather than the category list #1040 asked for, because a **reparented** component breaks a spec just as thoroughly while category-level drift shows nothing — such a component is reported `MOVED`, not as an unrelated removal plus addition. It **warns, never fails** (#980: a new category costs nobody a test, and a removed one is legitimate when the image dropped a distribution we do not test), but never reads as clean without a verdict — an unreadable baseline, a **malformed** one, a failed request and a **200 carrying no categories** each report `UNKNOWN` with the reason named (#1012). **"Warns, never fails" was not a property of the first version, it was a claim, and the difference cost a whole run:** the comparison sat outside both try blocks and the baseline was validated only far enough to know `categories` was an object, so the most natural hand-repair — pasting the raw `GET /api/v1/all` body, whose values are `{type: template}` objects and not arrays of type names — parsed, passed, and threw `TypeError: types is not iterable` out of `globalSetup`, aborting with **zero tests executed** (`runguard`'s infra abort). The comparison is now `catalogVerdict`, a pure function that **cannot throw**, with `globalSetup` holding nothing but I/O — which is what makes the guarantee unit-testable instead of asserted, and the layering shows under mutation: dropping the shape guard costs *attribution*, dropping the outer catch costs the run. The **200-with-no-categories** floor is the same class of false verdict from the other side: `snapshotCatalog` is tolerant by design, so `{}`, `null` and `{"detail": "Not authenticated"}` all normalise to zero categories and used to diff as *every* category gone — 36 lines each claiming specs would time out, on a still-building registry. The writer already refused that state (`--min-categories`, default 20); the reader had no floor at all, and the floor is 0 here vs 20 there on purpose (a wrong baseline is permanent and silent; a real-but-small catalog is drift a human should still see). Accept expected drift with `npm run catalog:baseline`, which is a **committed** diff on purpose: a self-updating baseline would make every catalog change invisible exactly once. Traps encoded in `component-catalog-drift.ts`: `component_display_names` is a **metadata map, not a category** (189 entries keyed by the lowercased type name — folding it in would add a 37th pseudo-category listing every component twice; the *stronger* claim that it makes reparenting undetectable is false, since the keys are lowercased and only `policies`, 1 of the 189, is already all-lowercase); a removed category whose components all **survived elsewhere** must not claim "specs will time out", so the report counts and now **names** what actually vanished (a count alone left the reader hand-diffing the baseline in a mechanism whose whole claim is that the cause is named); and the category keys are **sorted**, because `componentIndex` is last-wins over a relation that is not 1:1 — with insertion order, one type registered by two distributions reported a phantom `MOVED` on an *identical* catalog, a warning no baseline refresh could ever silence. ### Writing Tests

- Use `test.describe()` and `test()` blocks; document steps with `test.step()`
- Tag every test with at least one tag (`@release`, `@regression`, etc.)
- Use helpers from `tests/helpers/` instead of writing raw Playwright calls

### Unit tests (our code, not Langflow)

Specs cover Langflow; **unit tests cover this repo's own code** — the `scripts/` that
generate the release signal, the guards that gate PRs, the automation that edits specs on
`main`, and the helpers under `tests/helpers/`. A unit test goes **next to the code it
covers**, named `*.test.ts` (`*.test.mjs` for the `.mjs` scripts) — e.g.
`scripts/lib/stable-tests.ts` → `scripts/lib/stable-tests.test.ts`. Run with
`npm run test:units` (TypeScript, `node --test` via ts-node's require hook) or
`npm run test:scripts` (`.mjs`); both gate every PR. Never validate a helper in a scratch
file outside the repo (#1017). Full rules — the runner trade-off, how to make a script
importable, `testMatch`/discovery gotchas — in `CONTRIBUTING.md` → **Unit tests**.

**Test validation checklist** before marking complete (from CONTRIBUTING.md):
1. Run with full trace (`--trace=on`) and verify steps match screenshots
2. Force a failure to confirm no false positives
3. Walk through in debug mode (`--debug`)
4. Confirm no backend errors logged (`🚨 Backend Error:`) — **this step is a real gate, not a formality: an HTTP error never fails the test on its own** (#1084)
5. Update `QA-CHECKLIST.md` coverage symbols

**PR review checklist** — request changes if any of these are missing:
- The PR links a **current-wave item** or an **approved exception issue** (follow-up / `daily-failure` / `community`, in severity order) — see `ROADMAP.md`
- `@stable` is present **or** its absence is explicitly explained: utility specs state the reason in the spec doc's **Tags** section; temporary removals are tracked via a GitHub issue (no spec doc change required)
- Spec doc exists under `docs/` mirroring the test's path under `regression/`
- Spec doc has all mandatory sections filled: **What this test validates**, **Tags**, **Validation criterion**, **External dependencies**
- `Last validated` field reflects the current Langflow release cycle (e.g.: `1.10.x`)

### Tag Semantics

Tags are split into two groups: **cross-cutting** (severity/layer) and **functional** (product area).

**Cross-cutting**

| Tag | When to apply |
|---|---|
| `@stable` | Team-validated test — runs in the weekly workflow; failures open an issue for triage |
| `@release` | Happy-path flows required before any deploy |
| `@regression` | Tests for previously fixed bugs |
| `@api` | Tests exercising REST API endpoints |
| `@components` | Canvas/sidebar component configuration |
| `@workspace` | Flow/folder/canvas management |
| `@database` | Tests with persistent saved state |
| `@mainpage` | Home/dashboard UI tests |
| `@destructive` | Test mutates account-wide state (e.g. deletes every project of the shared superuser). **Lane selector, not a severity:** `playwright.config.ts` excludes it from every normal run via `grepInvert` and CI runs it alone afterwards with `PW_DESTRUCTIVE=1` (workers pinned to 1). Run it locally with `PW_DESTRUCTIVE=1 npx playwright test --grep @destructive`. Do **not** combine with `@stable` — `daily-stable.yml` has no destructive lane, so such a test would silently never run there (#1010) |
| `@enterprise` | Test targets a Langflow **Enterprise** instance, whose surface the OSS nightly does not serve. **Lane selector, not a severity**, resolved together with `@destructive` in `tests/fixtures/lane.ts`: the lane selectors are mutually exclusive (a count is deliberately not stated — it went stale when `@serving` was added), and the enterprise one also pins `workers: 1` because an Enterprise instance runs password-first — there is no `auto_login` — and Langflow rate-limits `/api/v1/login` per IP, so parallel workers exhaust the budget and report product assertions as `429`s. Point `PLAYWRIGHT_BASE_URL` at the instance and run `PW_ENTERPRISE=1 npx playwright test --grep @enterprise`. Do **not** combine with `@stable` — there is no scheduled Enterprise lane, so such a test would silently never run (#1010) |
| `@serving` | **Lane selector**, the third and the only PARALLEL one, resolved with the other two in `tests/fixtures/lane.ts`. Targets the **same OSS nightly image under a different configuration**: serving-plane end-user identity (upstream #14443/#14550) is off by default and turned on only by instance-global env vars, so the cross-user memory boundary is unreachable from every other lane and a spec gating on the settings would skip everywhere (#1010's green all-skip). Start it with `./scripts/start-langflow-serving-identity.sh`, which parameterises the **three** container states the contract needs — `TRUST=true` (identities isolate), `LANGFLOW_SERVING_TRUST=0` (fail-closed **and** fail-silent: every request becomes `anon::<uuid>` and persists **nothing**, so naming the header without trusting it disables chat memory instance-wide while runs still answer `200`) and `LANGFLOW_SERVING_REQUIRED=1` (an identity-less request, and a whitespace-only one, are refused `401 END_USER_IDENTITY_REQUIRED`). Then `PW_SERVING_IDENTITY=1 npx playwright test --grep @serving`. **Parallel is a decision, pinned by `lane.test.ts`**: neither cause that serialises the other two applies — the variant keeps `auto_login` (no login budget to exhaust) and isolation is keyed per `session_id`, so serialising would cost ~4× wall clock for nothing. Precedence when several flags are set is `@enterprise` > `@serving` > `@destructive`, by how specialised an instance each demands, announced rather than silent. Do **not** combine with `@stable` — there is no scheduled lane (#1010). Measured on `1.12.0.dev37`/`dev38`; the four-configuration contract and the port-shadow trap the start script now fails on are in `docs/serving/end-user-identity-lane.md` |

| `@governance` | Catalog and model-provider policy — the operator-facing surface Langflow 1.12 ships in **OSS**, not only in Enterprise: `catalog-policy/*`, `model-provider-policy`, `policy-bundle{,/history,/rollback}`. Measured on `1.12.0.dev32` against an EE build of `release-1.12.0` — 25 of EE's 55 governance routes are in the nightly and the blocks are *enforced*; `sso/*`, `authz/status|check|admin/*`, `enterprise-admin/*`, the admin UI and env-declared policy are the EE-only remainder. ## CI/CD

GitHub Actions workflows:

- **`pr-validation.yml`** — Runs on every PR to `main`. Parallel jobs: TypeScript check (`tsc --noEmit`, plus the two unit lanes — `npm run test:scripts` for the dependency-free `.mjs` helpers under `scripts/`, and `npm run test:units` for everything in TypeScript), ESLint, the **QA-CHECKLIST guard** (generated blocks untouched + spec↔doc↔checklist triad, see below), and the impacted-specs E2E run. All must pass before merge. The E2E job shares one Langflow service container between its `Collect models` pre-flight and the specs, so it carries the same two guards as `daily-stable.yml` (#1019): `PLAYWRIGHT_RETRIES=0` on the pre-flight, and a health gate between the two steps that waits out the post-sweep wedge (#922/#927) and, when it does not clear, fails naming the real cause instead of letting `globalSetup` report an unattributed 120 s timeout. Both are gated on `needs_models`, so an LLM-free PR pays for neither. **The E2E work is selected by import graph, not by changed-spec glob** (`scripts/impacted-specs-by-import.mjs`, #1054): a changed helper or Page Object selects the specs that import it **transitively**, because selecting only changed `*.spec.ts` let the highest-reach change the repo can receive run zero specs (PR #1052 changed a helper reached by 112 specs; PR #1088 one imported by 135 — both reported `skipping`). A changed spec still selects itself, so the old behaviour is a subset. `tests/fixtures/**`, `playwright.config.ts` and the global hooks are **suite-wide**: they resolve to every spec and raise a visible warning telling the reviewer to dispatch `manual.yml` for the full run. The selection is capped (`IMPACTED_SPEC_CAP`, default 20, `@stable` first within each tier) and **never silently** — the dropped specs are listed in the job log and the run summary (#1012's rule). **A CI-only diff no longer skips** (`scripts/ci-change-coverage.mjs`, #1159): nothing under `tests/` imports a workflow, so the import graph honestly returns zero and the lane used to prove only that the change *parses* — PR #1157 rewired four workflows onto a new composite action with every check green and the E2E lane `skipping`. The classifier answers the other half — *does the PR lane run what changed?* — deriving reachability from the YAML itself (a workflow's `scripts/x` refs plus its `uses: ./.github/actions/y`, and each action's own refs, which is how `wait-for-backend.mjs` is reached without being named in `pr-validation.yml`). Verdicts: **`canary`** (the lane's own workflow, an action it uses, or a script it reaches changed) runs a fixed 3-spec set — two `api/flows` specs plus one UI spec, all `@stable` and LLM-free — so the lane boots Langflow and walks pre-flight → health gate → Playwright for real; **`dispatch`** (the surface belongs to another lane) names the workflows to dispatch instead of implying coverage; **`none`** stays silent. A canary run **forces** the `Collect models` sweep, because the gate is `if: needs_models` and would otherwise be skipped by the very run meant to cover it — and neutralises both consequences so a drained key cannot block a CI-only PR: the sweep becomes `continue-on-error` and the credential pre-flight is skipped (#980's trade, #884's check). A verdict the classifier cannot produce fails the step rather than degrading to `skipping`, and a canary spec that no longer exists aborts with exit 2. **Whether the lane needs the provider sweep — and whether it would run a spec bare without one — is a second, separate verdict** (`scripts/provider-dependent-specs.mjs`, #1216), because the inline rule answered only the first and let the second resolve silently to "run it anyway". PR #1152 changed one helper, the import graph correctly pulled in all 7 of its callers, `needs_models` came back `false`, `Collect models` was skipped, and `core-components/agent-component-regression.spec.ts` then ran with no provider and died on `value-dropdown-model_model` — a spec that is `@stable` and green in the daily, so the lane emitted a red that had nothing to do with the diff. The old rule asked *does this spec resolve a model* (area + marker references); the real question is *does it need a provider configured at all*, which the suite's own `@agents` / `@model-provider` tags answer declaratively. The verdict then turns on what the PR is **about**, because forcing the sweep for every provider-dependent spec would re-couple unrelated PRs to key health (`Collect models` is a hard gate here — the #915/#910/#911 cost): a provider-dependent spec **the PR changed itself** forces the sweep and runs, one pulled in because something it **imports** changed is **excluded and announced** (`::warning::` plus the step summary, naming the specs, the reason, and where they *are* covered — #1012's rule). A spec that **consumes** the sweep's output (`models.json`, the resolvers) still forces it either way: those fail at setup without it and have always been in scope, so excluding them would remove coverage that exists today — an asymmetry argued in the script's header rather than left to look like an oversight. `@playground` is deliberately not a provider tag. **"Changed itself" is read from the PR's changed-file list, never from `impacted-specs-by-import.mjs`'s `.direct`** — that field holds every *depth-1 importer*, so on #1152's one-helper diff all 7 callers were `direct`, and reading it as "the PR changed this" forced the sweep for precisely the case the fix exists for. It survived a hand-built fixture (`direct: []`) the real resolver never emits, which is why the unit lane now feeds the verdict the **resolver's actual output** on that diff. **Excluding *every* selected spec forces the sweep instead**: decoupling from key health is worth one spec's coverage, never worth all of it, since an empty run list skips the E2E job and a lane that runs nothing is no evidence at all. The re-derivation of the run list is also **skipped on a canary run** — a canary's specs come from `ci-change-coverage.mjs`, not the import graph, so overwriting them with the (empty) verdict list would blank `$SPECS`, trip `has_specs=false` and skip the job together with `Collect models` and the health gate, reopening #1159's hole. Both are pinned structurally. When the exclusion empties the run list the job's own `has_specs` gate skips the E2E run, which is the only safe outcome (`npx playwright test` with no paths runs the whole suite) and honest only because the warning always accompanies it. One behaviour tightens on the way: the old inline loop used `grep -q … 2>/dev/null`, so a spec it could not read counted as "no match"; the verdict now treats an unreadable spec as **undecidable** and fails the step, because defaulting to LLM-free there is how a provider-dependent spec would run bare again. The run list is emitted to `$GITHUB_OUTPUT` exactly once, after the verdict re-derives it — pinned by a structural test, since an early second write would leave which value wins up to the runner and let an excluded spec reach Playwright anyway. **The run summary is rendered by `scripts/render-impacted-summary.mjs`, not by inline shell** (#1226). Three wrong figures shipped out of that block while it lived in the YAML, each with every gate green: `running in this PR` was `TOTAL - DROPPED`, so a provider-excluded spec counted as executed; the same line read `0` on a **canary** run, where `TOTAL` is 0 by definition while three specs do run; and the `@stable` tally beside it was the resolver's `stableSelected`, scoped to `selected` (post-cap) while the total was `.specs` (pre-cap), so the pair read as one breakdown of two different sets (a `get-auth-token.ts` diff printed `178 … @stable: 20`, where the true figure for 178 is 155). Each fix added another regex over the workflow text, and each of those regexes was then shown to miss its own mutation — swapping the printed `$RUN_COUNT` for `$TOTAL`, or hoisting the caveats above the counts, both passed. **A guard that pins a spelling does not pin a behaviour**, which is why the rendering moved to a script whose tests assert on output: given a verdict that excluded one spec, the summary says 6, and says it above the caveats. Three things it now guarantees. The run count is the length of the list handed to Playwright, passed in as `--specs` and never recomputed. The counts come **first** — appending caveats as they occurred put the cap's dropped list (217 bullets on a suite-wide change) above the figure a reviewer opens the summary for, which answered #1226 in letter only. And a verdict that aborts **degrades instead of erasing**: the resolution line and the caveats still establishable are printed with the gap named, where the buffered version it replaced left a 0-byte summary. The `@stable` tally comes from the verdict's `stableRun`, counted over the surviving run list inside `provider-dependent-specs.mjs` (which already reads every selected spec's source, so this costs no `grep` in the YAML), is **omitted** on a canary run where the verdict never saw those specs, and reads `@stable` from a `tag:` array rather than anywhere in the file — the loose substring test overcounted 8 of 235 specs, one of whose only occurrence is the comment "`@release`, never `@stable`". The strict predicate yields 170 files, matching what `scripts/stable-tests.ts` derives from the spec ASTs. The `::warning::` annotations stay inline in the workflow: they are log-level, unaffected by ordering, and they are what still tells a reviewer the run was shortened if the step dies before it can render.
- **`nightly.yml`** — **Dormant: `workflow_dispatch` only.** The `schedule` block is commented out in the workflow ("disabled until the suite is stable in production"), and the last run was 2026-03-19 — so despite the name this does not run nightly. When dispatched it targets `langflowai/langflow-nightly:latest` and opens a GitHub issue on failure assigned to @Victor-w-Madeira. Re-enabling is uncommenting the cron.
- **`daily-stable.yml`** — Runs on weekdays (Mon–Fri) at 05:00 BRT against `langflowai/langflow-nightly:latest`; runs only `@stable` tests; opens a GitHub issue on failure for triage (`daily-failure` label); appends one entry to `reports/daily-history.jsonl` and commits it back to `main` with `[skip ci]` (runs on success and failure). **This is the active stable workflow.** The `Collect models` pre-flight step shares the Langflow container with the `@stable` run and can leave it **wedged** (container alive, event loop blocked — #922/#927), so three guards keep that from costing the run: `LANGFLOW_WORKERS=1` on the service, `PLAYWRIGHT_RETRIES=0` on that step, and a health gate between the two that waits for the backend and fails with the real cause named if it does not recover (#1011). A red `Collect models` **does not** abort the shard — a drained provider key must not kill the specs that never touch it (#980). Two independent report guards run in the merge job: `shardguard` (every shard produced a blob → results are not under-counted; it runs `if: always()` so its verdict exists even when no shard produced anything to download) and `runguard` (`scripts/check-run-integrity.mjs` — the merged report actually contains tests). A **zero-test run is an infra abort, not a per-test day**: it fails loudly (fail-closed — an unknown `runguard` verdict fails too), is barred from both paths that write on the strength of the report (`@stable` auto-removal and the `spec-durations.json` refresh), and opens an issue titled *"executed ZERO tests"* instead of the usual per-test body — even when the `test` job came back green, which `--pass-with-no-tests` makes possible (#1012). **`reports/spec-durations.json` — the table that makes sharding duration-balanced (#936) — had never been written once until #1252, and the shape of that failure is worth carrying:** the refresh required `needs.test.result == 'success'`, which on a suite with 1–10 hard failures a day is not strict but *closed* (zero of the six dailies after #936 qualified; only 2026-07-03 in 23 entries ever had `failed: 0`, three weeks before the mechanism existed), so every daily partitioned by **file count** and one red spec out of 430 discarded 429 valid measurements. The distortion the gate guarded against is now excluded per file instead — a file counts only when every `@stable` test in it came back `expected` (Playwright's word for "passed with no retry"), `flaky` and `skipped` are both out (a skipped file measures ~0 s and would ride free onto the heaviest shard, which the green-only gate never prevented either), an absent status is undecidable rather than a pass, and **every other current file carries its committed value forward**, which is what makes dropping the gate a fix rather than a loosening. Two consequences to know: the step must never `>` into `reports/spec-durations.json`, because that path is now also its input and the redirect truncates it before `node` opens it (silently degrading to "measured this run only" — pinned by a structural test); and `mode=count` in the prep log is now accompanied by a `::warning::`, because it was always printed and nobody read it as a problem, which is how weeks of cold starts passed unnoticed. Three details of the wiring are load-bearing and pinned structurally, all three found in review of the fix itself: the step is **`if: always() && <runguard gates>`**, because a step `if:` with no status function gets an implicit `success()` and the report upload / payload build ahead of it are not `continue-on-error` — a transient artifact-upload failure would silently skip the refresh again; it is **`continue-on-error`** (#980's trade — the table is an optimisation, not a verdict, and a crash in it would otherwise redden a green daily while `Create issue on failure`, gated on the *test* job, opens nothing); and `mode` is computed over the **intersection** of the table with the files being partitioned, not over the table's size, since a table whose every key is stale (one spec-directory rename) leaves every file at the same fallback weight — a count balance labelled `duration`, with the warning suppressed on the one day it was true. One measurement is refused for the same reason `skipped` is: a file that looks clean but measures **0 s** is unmeasured, not light, and a zero in the table is a file `buildShards` can never find a lighter shard than, so all 171 would land on shard 1 (reachable in one step the day a reporter change stops emitting `duration`) — `buildShards` also treats a non-positive weight as unknown, so a hand-edited table cannot reach that state either. **The per-file rule is right one file at a time and biased in aggregate, which is what #1326 corrects:** a file is excluded when it failed, flaked or skipped, and the specs that do that here are the ones calling a real model — the slowest ones — so the table converges *on the cheap files* and the median of what is measured underweights what is not (global median 16.3 s against neighbourhood medians of 23.3–30.5 s for the eight files currently missing). The issue's own proposal — weight an unknown file at its **directory** median — was measured and **rejected**: as a point prediction it looks better (leave-one-out MAE 13.5 s vs 15.1 s), but two of the eight real cases sit in directories mixing cheap API specs with one expensive UI spec and it weights them **0.7 s and 0.5 s**, 23× and 33× lighter than today, and scored on what the daily actually waits for — the **makespan** of the partition against the true durations — it is not better at all (hiding the K heaviest, K = 4..40, N = 4: mean excess over an oracle partition **101 s** for the global median vs **113 s** for the directory median floored at it; 300 draws sampled ∝ duration: 75 s vs 77 s). LPT is robust to underweighting a minority of files. What helps, with no second mechanism, is raising the **quantile** — an unknown file is a risk and over-weighting is the safe direction, since LPT then places it first onto an empty shard rather than last onto a full one — so the fallback is the **p75** of the measured files, which beat the p50 in all 8 (shard count × regime) cells measured and in 1107 of 1912 decided paired draws at N = 4 (mean excess 79.8 s → 75.0 s; the p100 degrades to 92 s). Keep the size of it in view before re-opening: the fallback costs ~75–100 s of makespan on a ~950 s shard and nothing tried recovers more than ~25 s. The other half is reporting — `matrix` now **names** the unmeasured files and the weight they got (capped at 30, elided count printed), because "170/178 with a recorded duration" reads as a rounding error while hiding that the missing ones are the expensive ones and that a heavy spec red for a month is invisible in it (#1012). One claim of #1326's is **wrong** and is now pinned rather than restated: `@destructive` cannot be an unmeasurable entry in the partition input, because the tag is **per test** — `folder-deletion-integrity`'s destructive test is `@release @api` while its three `@stable` tests run in the normal lane and measure 22.9 s — and `playwright.config.ts` `grepInvert`s `/@destructive/` where a CLI `--grep` cannot override it, so 0 of the 459 specs the prep job lists carry it.
- **`weekly-stable.yml`** — **Disabled** (kept as a fallback, superseded by `daily-stable.yml`). When enabled it runs every Monday with the same machinery, writing to `reports/weekly-history.jsonl`.
- **`manual.yml`** — Parameterized manual run; accepts a Docker tag or full URL, a specific test suite, and an optional grep filter. Two further inputs exist for the **#1187 adoption gate** and only that: `any_completion_provider: ollama` routes every spec declaring `tier: "any-completion"` to this job's keyless Ollama service (no key, no quota — the resilience answer to a drained account), and `retries` lets a dispatch measure a candidate with retries off. **The gate is a measured RATE over a stated N, not *passes 3/3*** — that wording shipped with #1212 and was refuted by the first thing it certified: the pilot `agent-system-prompt` measures ~60 % routed (9/15, CI and a dev box agreeing), and at p=0.60 a three-run gate certifies with probability ≈22 %, so it did. No feasible N/N fixes it (~59 consecutive passes for 95 % confidence in p ≥ 0.95), which is why the criterion moved from counting runs to **dependence**: `any-completion` means no assertion depends on the model *choosing or managing* to do anything, and that includes timing — `agent-component-regression` passed 5/5 routed and is still `tool-calling`, because its Stop-button test needs the run to still be in flight and its interaction suite needs three turns (one long-form) inside the 5-minute cap on a model `ollama-provider.spec.ts` measures at >100 s per call on a runner. Evidence must also be the **spec on the lane**: the same 1B complies 10/10 called directly and 60 % through the Agent, so a model-alone probe measures a different system (#1187). Both are set as **job-level** `env`, because `.github/actions/run-e2e` declares per-step `env` that ADDS to the job environment rather than replacing it — the same path the three `OLLAMA_*` vars already take, so the shared action is untouched. The **external-URL** job **fails** when routing is requested instead of ignoring it: that target is not on the runner's network, so it cannot reach the service container, and honouring the input silently would run the routed specs on a hosted provider while the dispatch summary said `ollama` (#1012's rule). A third input, `provider`, makes this **the only lane that can still run multi-provider** (#1186): `auto` (default) keeps one model per active provider, `openai` / `anthropic` / `google` pin to that provider's **settled** model, and `all-models` sweeps the whole catalog — resolved by `scripts/select-manual-model-target.mjs`, never by inline `env:`, because `MODEL_TEST_PROVIDER` alone *widens* the run to that provider's entire catalog and a hardcoded id skips silently the day CI loses access (#1169's two traps). It exists because multi-provider used to be the default **by omission** and both scheduled lanes have since opted out — `pr-validation.yml` pins openai (#1169), `daily-stable.yml` rotates by weekday (#1185) — leaving no lane that runs it and no input to ask for one. **The rotation's window is wider than #1185 recorded:** "≤3 days" is the intra-week gap, but the cron is Mon–Fri, so the real per-provider latency is ≤4 days for openai and anthropic and **≤7 days for google** (Wednesday's only slot) — the provider of #963. Those are best cases, not bounds: the rotation advances past an inactive provider, so a Wednesday with a dry google key costs google its whole week. Hence the recorded cadence: one `provider=auto` + `test_tag=@stable` dispatch per Langflow release-candidate cycle, **≥2 business days before sign-off**, owned by whoever signs the release validation, plus ad-hoc `provider=<x>` dispatches when triaging a provider-specific red. **Failure semantics deliberately differ from the two sibling lanes**, and reading them as the same will look like an inconsistency: there the pin is an optimisation the lane applies to itself, so it declines and falls back to the costlier multi-provider run (#980 — losing a scheduled day costs more than spend); here the input **is** the request, so a selection that cannot be honoured **exits 1** with the cause named (no `continue-on-error`), because continuing would run the other providers, answer a different question and report success. This lane is never scheduled, so that costs a re-dispatch, not coverage. `auto` emits nothing and no state of the catalog can fail it, which is what makes "the default is unchanged" a property rather than a promise — **but it is not silent, and that distinction is the point:** `collect-models` writes `models.json` only at the *end* of its sweep and is `continue-on-error` here, and with no catalog `resolveTestTargets()` returns **one** `provider:openai (fallback)` target whose `skipReason` is `undefined` (the health map is empty on an absent `providers.json`), while openai's key *is* forwarded — so ~30 parametrized agent tests would run one provider, green, under a log line promising multi-provider. `auto` therefore reads the catalog for reporting only, prints the fan-out it derived from it, and warns when that fan-out is not multi-provider. **It reads `providers.json` too, and that is the likelier of the two failures:** the resolver takes its targets from `models.json` and then attaches `providerSkipReasons()` from `providers.json`, so a provider the probe recorded `inactive` still yields a target — one that `test.skip()`s — and the two files disagree by construction, since `collectAll()` scrapes the model lists in step 2 and validates the keys only in step 3 (`models.json` mirrors the Langflow catalog, not the validation; a capped Google key left all 36 google models in it, #1029). Counting the catalog printed *"Resolves 3 target(s)"* for a dispatch where two of the three skipped — the same overstatement as the absent-catalog case, by the route this account has actually been down three times (#772 openai, #1029 google, #1169 anthropic) — so the count, the warning and the printed line are all over the **runnable** targets, with the skipped ones named alongside the reason `collect-models` recorded. Reading the health file is **fail-open**, mirroring `readProviderHealth()`: absent or unparseable means no signal, nothing skips, so those targets count as runnable and the unverified fan-out is warned about rather than assumed dead. One more thing only this lane can hit: `any_completion_provider` and `provider` can both be set, and routing **outranks** the pin for `tier: "any-completion"` (#1187) — the specs announce that themselves but only mid-run, so the step announces it at dispatch time. `all-models` declines outright when `models.json` is absent or empty, since `ALL_MODELS=true` over an empty catalog resolves one `(fallback)` target per spec — the opposite of the sweep, logged as a success — and when it does sweep it announces the size **and** that an unnarrowed sweep will not finish inside the job's 90-minute timeout. The **external-URL** job rejects any selection but `auto` for the same reason it rejects `ollama` routing: it runs no `Collect models` (that would write our keys into an instance we do not own, #1055) and receives no provider key, so every parametrized LLM spec skips there regardless and honouring the input would produce the green all-skip #570/#1012 exist to prevent.
- **Self-hosted echo endpoint (`go-httpbin`)** — Every lane that runs echo-dependent specs (API Request component, the agent fetch-tool specs) starts a `ghcr.io/mccutchen/go-httpbin` service container and resolves `ECHO_BASE_URL` to it via `.github/actions/resolve-echo-endpoint`, so those specs never call the public internet. Built for `daily-stable.yml` (#462/#639) and extended to `pr-validation.yml`, `nightly.yml` and `manual.yml` in **#1128**, after PR #1133 lost three specs to an `httpbin.org` 504 that read like a product failure. Two things make this non-obvious and are encoded in the action: Langflow's `validators.url()` **rejects a single-label host**, so the variable must be a raw container IP (never `http://go-httpbin:8080`), and its SSRF layer blocks private addresses unless the RFC-1918 CIDRs are in `LANGFLOW_SSRF_ALLOWED_HOSTS` and blocks loopback outright — so the address the **job probes** (`localhost:<mapped port>`, on host-based lanes) is not the address **Langflow calls**. The failure mode differs by lane on purpose: `mode: fail` on PR/nightly/manual, because a silent fallback to the public host is what made #1128 look like a product bug, and `mode: warn` on the daily, where a day of coverage outweighs strictness (same reasoning as `Collect models`, #980). The decision logic lives in `scripts/resolve-echo-endpoint.mjs` and is covered by `npm run test:scripts`. `manual.yml`'s **external-URL** job is scoped out — it targets a Langflow that is not on the runner's network and cannot reach a service container.
- **Post-collect-models health gate (`.github/actions/wait-for-backend`)** — Every lane that shares one Langflow container between its `Collect models` sweep and its test run polls `/api/v1/version` between the two, through this one action: `daily-stable.yml`, `pr-validation.yml`, `manual.yml` and `weekly-stable.yml`. The sweep can leave the backend process-wide **wedged** (container alive, healthcheck green, event loop blocked — #922/#927); `globalSetup` polls 120 s and then throws, so a wedge that outlasts that window costs the whole lane and reports itself as an unattributed preflight timeout. The gate buys two things: a longer window for the wedge to clear (recovery is real and measured — 223 s on #1019, 260 s on #1044's dispatch, every second of it gunicorn's own `WORKER TIMEOUT` → `SIGKILL` → ~12 s restart), and, when it does not clear, **attribution** — its `::error::` names which state it observed (refused → dead; accepted-and-unanswered → the wedge; non-2xx → an application failure that is *not* the wedge), unconditionally, on every run. It was three copy-pasted shell loops until **#1045** (`#1011` daily → `#1019/#1044` pr-validation → `manual.yml`) and they had already diverged on the deadline, the heartbeat and the attribution, while `weekly-stable.yml` — the documented fallback — had no gate at all. One deadline now: **420 s** for every lane, over-waiting being nearly free because the extra time is only ever spent on a lane already headed for a red. The loop lives in `scripts/wait-for-backend.mjs`, exercised by `npm run test:scripts` against all four backend states (healthy / dead / wedged / wedged-then-recovers) plus a structural guard that the gate still sits between `Collect models` and the run step in all four workflows — the wedge itself cannot be reproduced on demand, since it depends on the runner's collect-models load. A failed sweep is surfaced here as a `::warning::` and never gates the run (#980/#570).
- **`--grep` composition (`scripts/build-grep-filter.mjs`)** — Playwright honours exactly **one** `--grep`, so a lane wanting "tag AND name" — or "`@destructive` AND whatever the dispatch asked for" — has to AND its filters itself as a lookahead chain. Four lanes did that inline, interpolating each fragment **unparenthesised** (`--grep "(?=.*${TEST_TAG})(?=.*${TEST_GREP})"`), and alternation has the lowest precedence inside a group — so a fragment containing `|` did not go in as a unit. `test_tag=@stable` with `test_grep=@agents|@model-provider` selected **48 tests / 26 files where the correct filter selects 81 / 37**, byte-identical to asking for `@agents` alone: the dispatch was accepted, the job was green-path, and nothing in the log or the summary said the run was narrower than requested (#1012's rule). It cost real coverage during the 1.11.2rc3 release validation (#1275). **The mechanism is positional, and the obvious reading of it is wrong in a way that decides whether a test fixture can catch it.** Lookaheads are zero-width, so every lookahead in the chain is evaluated at the **same** starting position and the engine may try any position — a `.*`-prefixed branch is position-insensitive, a bare branch like `@model-provider` pins the start to where that token begins, and every other lookahead must then match from there onward. The broken filter therefore asked *"@model-provider appears, AND @stable appears at or after it"*, unsatisfiable here only because `@stable` is declared **first** in essentially every `tag:` array (55 specs are `["@stable", "@regression", "@components"]`). So the defect is **order dependent**: the same bug leaves the selection accidentally correct whenever the alternated token happens to come first, and a fixture using that ordering **passes against the bug** — which is why the tests assert both orderings. Fixing it in the YAML was one character per side, and rejected for that reason: the only available guard would be a regex over the workflow text, and #1226 established that such a guard passes the mutations it exists to catch. The composition lives in the script so `npm run test:scripts` covers it by **selection** — each case compiles the composed filter and runs it against real suite titles (reverting the wrapper fails 3 of them). Four further properties it guarantees: a **single** fragment is passed **verbatim**, so the overwhelmingly common `--grep @stable` path is on exactly the string it used before; **no** fragments means no `--grep` at all rather than an empty regex, which matches every test and would turn a narrowed dispatch into a full-suite run; an invalid fragment is refused **there**, naming it, instead of reaching Playwright as a composed string whose error points at the composition (`shell: bash` runs with `-e`, so `FILTER=$(…)` failing aborts the step); and the wrapper is `(?:…)`, never `(…)`, which would renumber a backreference the caller wrote inside its own fragment. One accompanying test **is** structural, and it pins an **absence**, not a spelling: no YAML under `.github/` composes a lookahead around an interpolated variable. It cannot tell whether a lane composes correctly — the behaviour tests do that — but the bug reached four lanes by copy-paste, so a fifth is how it returns. Independently, `nightly.yml` read `test_grep` as `${{ … }}` **inside** `run:`, which the `run-e2e` action explicitly forbids for its own inputs: substitution happens before bash parses the line, so a dispatch value like `"; rm -rf` breaks out of the string — both of its steps now take it through `env`.

A `since` input exists so a dispatch after a long gap can cover more than 24h. The 14-area table (13 until #1581 added `Catalog & Provider Policy`, and made an area able to declare the commands it prints rather than deriving one from its tags — `@governance` is lane-gated, so the derived form selected zero tests), the `src/lfx/` decision record and both guards live in `scripts/watch-upstream-areas.mjs` (#1092, covered by `npm run test:scripts`); the workflow only wires them. ## Run history (`reports/`)

Append-only JSONL log of CI runs, committed to the repo so longitudinal questions ("how many weeks did test X fail in a row?", "did failures correlate with a Langflow upgrade?") can be answered without paying for an external dashboard or extending artifact retention.

- **`reports/daily-history.jsonl`** — One line per `daily-stable.yml` run (the active stable workflow). Written by `scripts/append-weekly-history.mjs` (shared appender, pointed here via the `HISTORY_FILE` override) and committed back to `main` with `[skip ci]` at the end of the daily workflow (even on failure, so recurring breakage is captured).
- **`reports/weekly-history.jsonl`** — Frozen history from `weekly-stable.yml` (now disabled). Same schema; retained for past longitudinal queries.
- **`reports/README.md`** — Schema (version 1), expansion criteria, and example `jq` queries. Read this before extending the mechanism.

The JSONL files are **machine-written and human-read only** — never hand-edit. The schema is versioned; backwards-compatible additions ship without a version bump, breaking changes bump `version` and the script branches on it. Adding a new source (e.g. `nightly-history.jsonl`) requires meeting the three expansion criteria documented in `reports/README.md` — in particular, a different failure lifecycle from existing sources.

Triage rules driven by this history (when to remove `@stable`, when to open an issue for a recurring flake) live in `CONTRIBUTING.md` under "Tag @stable — validated tests".

## REGRESSIONS.md — the Regression Ledger

Curated, append-only registry of the real Langflow regressions **the suite caught**, and the source of the ROI indicator at the top of the file. A row is added only when all three hold: a confirmed `langflow-regression` verdict, adversarial (refute-first) validation, and a filed upstream ticket (Jira `LE-####` or a `langflow-ai/langflow` issue). Confirmed but unticketed goes under **Candidates**; a finding validation downgrades to a non-user-facing gap is listed nowhere. Regressions the team confirms by hand, outside the suite, stay on the Jira board — every row must trace to a spec failure or spec-validation run recorded in a repo issue.

The block between `<!-- REGRESSIONS:START -->` and `<!-- REGRESSIONS:END -->` is **auto-generated** — never hand-edit it, and never hand-edit the counts. Edit the `## Ledger` table only, then run `npm run regressions:summary` to regenerate the block and commit both. Logic lives in `scripts/regressions-summary.ts`; it is idempotent and aborts rather than emitting a wrong count (bad marker order, missing/empty `## Ledger` section, wrong column count, invalid `Severity`/`Status`, an `Area / Test` cell without the `area · spec-file` separator, or two rows with the same `Upstream` ticket).

Unlike `QA-CHECKLIST.md`, the generated block here **is** committed in the PR that adds the row — the file changes a handful of times per quarter, so the collision risk that forced the checklist guard (issue #741) does not apply. The `pr-validation.yml` typecheck job runs `npm run regressions:check`, which fails the PR when the committed block disagrees with the table.

## QA-CHECKLIST.md

Two passages in `QA-CHECKLIST.md` are **auto-generated**:

1. The **Coverage Summary table** is derived from the bullet markers (`[x]` / `[-]` / `[ ]` / `[~]` / `[!]`) inside Part II. Never propose manual edits to the table's numbers, percentages, or `**TOTAL**` row — only edit the bullets, and the workflow regenerates the table on the next merge to `main`. Logic lives in `scripts/coverage-summary.ts`. If a new module section is added to Part II, update the `MODULES` array in the script.
2. The **Coverage Summary Note** and the **`Phase 0 — Validated`** block (header counts and bulleted list) are derived from `@stable` `test()` calls parsed out of `tests/tests-automations/regression/**.spec.ts`. Never edit those by hand. Add or remove the `@stable` tag on the relevant `test(...)` and the workflow regenerates on the next merge to `main`. Logic lives in `scripts/stable-tests.ts`.

Both regenerators run together via `npm run coverage:summary` and are idempotent — a second run produces no diff when in sync.

> **In a PR, edit ONLY the manual Part II bullets — do NOT run `npm run coverage:summary` and commit its output.** The generated blocks (Coverage Summary table + note, `Phase 0 — Validated` list, Phase 1/2 tables) are regenerated on merge to `main` by `update-coverage-summary.yml`. Committing regenerated counts in a PR makes concurrent `@stable` PRs collide on the same count lines (the recurring `QA-CHECKLIST.md` conflict — issue #741). `npm run coverage:summary` is for local inspection only; the `pr-validation.yml` **QA-CHECKLIST guard** job (`scripts/check-checklist-guard.mjs`) fails any PR that edits a generated block.

> **The bullet itself is mandatory.** The same job runs `npm run check:checklist-coverage` (`scripts/check-checklist-coverage.ts`), which fails the PR when a spec carries `@stable` **or** has a spec doc under `docs/` but no manual Part II bullet references it — that spec would otherwise be invisible in every generated count (issue #985). Only the hand-written region counts as a reference: the generated `Phase 0` block echoes every `@stable` basename, so matching the whole file is vacuous. A missing mirrored doc is **not** a defect — docs resolve by content reference, not filename.

## Playwright Configuration

Key settings in `playwright.config.ts`:
- Base URL via `PLAYWRIGHT_BASE_URL` (default: `http://localhost:7860`)
- Chromium only, with clipboard permissions
- Fully parallel, 5-minute timeout per test
- 3 retries locally, 2 retries in CI; trace captured on first retry
- HTML reporter locally, blob reporter in CI
- Browser locale `en-US` by default, resolved by `tests/fixtures/locale.ts` rather than
  hardcoded (#1400): a spec opts out with `test.use(withLocale("pt-BR"))`, a whole run
  with `PW_LOCALE`, and an invalid tag aborts the config instead of falling back to
  English. **It does not decide the language Langflow renders** — measured on
  `1.12.0.dev20`, the UI reads `localStorage.languagePreference` and never
  `navigator.language`, so under `pt-BR` every string stays English and `<html lang>`
  stays `en`. What it does govern is `Intl` formatting and the document
  `Accept-Language`. The backend's `set_locale` middleware is a **partial** third axis,
  not a "no": Langflow localises by `Accept-Language` (`/api/v1/flows/basic_examples/` →
  `Sugestões básicas` under `pt`), and while the frontend pins the header on the calls
  that pass through its axios interceptors — 17 of 20 on the home screen — the other 3
  (a `/api/` subresource, two `/api/v9/invites/` XHRs) carry the context locale, so a
  spec asserting on the backend's locale must set the header itself. `CONTRIBUTING.md` →
  *Browser locale* has the three-axis table and the measurement. Pinned behaviourally by
  `tests/fixtures/locale-gate.spec.ts`, the sibling of the two error-policy gates
